## 一、team-api 当前调度实现

team-api 的调度核心在两处：算法层 `relay/scheduler/scheduler.go`，编排层 `internal/logic/relay/provider.go` + `relay/handler/relay_handler.go`。

### 1. 调度入口与候选构建

`DataProviderImpl.GetChannelForModel`（`internal/logic/relay/provider.go:98`）→ `selectChannelFromDB`（`provider.go:120`）：

- 从 `chn_abilities`（模型→渠道映射）JOIN `chn_channels` + `chn_health_scores` 拉候选，过滤 `enabled=true`、`status='active'`、租户渠道范围、排除已失败渠道（`excludeChannelIDs`）。
- 有 feature flag **`channel_scheduler_v2_enabled`** 控制两套路径：
  - **关闭（legacy）**：按 `priority DESC, weight DESC` 排序，取第一个能取到上游 key 的渠道（`provider.go:162-195`）。纯优先级首选，无随机、无健康度。
  - **开启（v2）**：构建 `[]scheduler.ChannelCandidate`，交给调度引擎（`provider.go:197-279`）。

### 2. 优先级 + 权重 + 健康度选择算法（`relay/scheduler/scheduler.go`）

`Select`（`scheduler.go:49`）算法注释明确：

1. 排除 `Weight <= 0` 的渠道；
2. 排除 `HealthScore < 20` 的渠道（若全不健康则保留全部，避免饿死）；
3. 按优先级分组，**取最高优先级组**（`groupByPriority` 升序排，`groups[len-1]` 即数值**大**优先——与 new-api 一致，与 sub2api 相反）；
4. 组内**加权随机**（`weightedRandomSelect`）。

**健康度降权**（`effectiveWeight`，`scheduler.go:185`）：健康度 50-79 权重减半，20-49 降至 1/4，最低保 1。即不健康渠道不直接剔除，而是降低被选概率。

**`SelectStable`**（`scheduler.go:65`）：在最高优先级组内，**优先用亲和渠道**（`preferredChannelID` 命中即直接返回），否则用 **Rendezvous 一致性哈希**（`weightedRendezvousSelect`，`scheduler.go:164`）做加权选择——相同 seed + 候选集在**不同进程/实例得到相同结果**，适合多实例部署的冷请求。seed = `tenant:user:apikey:model` + 时间桶（桶长 = 亲和 TTL）。

### 3. 渠道亲和性（`internal/logic/relay/affinity.go`）

- **key**：`sha256(tenantID:userID:apiKeyID:modelName)` → Redis 存 `channelID`，TTL 默认 **1800s**（`channel_affinity_ttl_seconds` 可配）。
- **反向索引**：`relay:affinity:v2:channel:<channelID>` 维护该渠道绑定的所有 key 集合，渠道失效时 `InvalidateChannelAffinities`（`affinity.go:80`）用 Lua 脚本批量清除——避免脏亲和。
- **feature flag** `channel_affinity_enabled` 控制。
- **流程**：`selectChannelFromDB` 先 `getAffinity` 拿 preferredChannelID → `SelectStable` 在最高优先级组内优先命中；成功后 `SetChannelAffinity` 写回；硬失败 `DeleteChannelAffinity`（`provider.go:222-275`）。
- **关键限制**：亲和**只在最高优先级组内生效**。若亲和渠道不在当前最高优先级组，会被降级处理（`preferredChannelID=0` 或删除亲和，`provider.go:239-246`）。

### 4. 失败重试（`relay/handler/relay_handler.go:417`）

```
maxRetries = 3   // 即最多 4 次尝试（attempt 0..3）
for attempt := 0; attempt <= maxRetries; attempt++ {
    selection = GetChannelForModel(..., excludeChannelIDs)   // 排除已失败渠道
    ...转发...
    失败 → excludeChannelIDs = append(..., selection.ChannelID) → continue
}
```

- **跨渠道重试**：失败渠道累积进 `excludeChannelIDs`，下次选号排除（`relay_handler.go:472/499/561`）。
- **容量溢出不消耗重试次数**：`acquireChannelLease` 失败时 `attempt--` 再 continue（`relay_handler.go:473`）。
- **重试触发判定**：
  - DoRequest 失败用 `IsRetryableForRequest`（`relay/constant/errors.go`）：状态码 **429/500/502/503/504** 或网络瞬时错误；**昂贵非幂等生成（图片/视频）对「模糊送达」错误不重试**，避免上游重复生成 + 重复计费。
  - DoResponse 失败：流式 / 不可重试 / `attempt>=maxRetries` / **`IsResponseWritten`（响应已写给客户端）** 任一满足即终止（`relay_handler.go:569`）——防止成功体追加到已写错误体后造成响应污染。
- **每次失败副作用**：`UpdateChannelHealth(false)` + `IncrementConsecutiveFailure` + `DeleteChannelAffinity`。

### 5. 健康度模型（`internal/logic/relay/health.go`）

- **综合健康度公式**（`calcHealthScore`，`health.go:96`）：
  `健康度 = 成功率×0.40 + 延迟分×0.25 + 稳定性×0.20 + 连续失败分×0.15`（0-100）
- **EWMA 平滑**：成功率 α=0.1（`new=old×0.9+sample×0.1`），延迟 α=0.3（`new=old×0.7+sample×0.3`）。
- **连续失败**：失败 +1，成功归零；连续失败分 = `100 - consecutiveFailures×20`。
- **自动禁用**：`checkAutoDisable`（`health.go:91`）连续失败达阈值自动禁用渠道。
- 这是个**混合模型**：EWMA 平滑的成功率/延迟 + 离散的连续失败计数，比 new-api 精细，但比 sub2api 的纯 EWMA（错误率 + TTFT）多了离散阈值。

### 6. 容量控制（`relay/handler/channel_lease.go`）

- `AcquireChannelSlot`：Redis 原子占并发槽，`MaxConcurrency` 超限则失败（Redis 异常降级放行）。
- `channelLease`：长请求 30s ticker 刷新租约（`refreshLoop`），结束 `Release`。

## 二、三项目对比总表

| 维度 | new-api | sub2api | **team-api** |
|------|---------|---------|--------------|
| 调度单位 | channel | account（订阅账户） | channel |
| 框架 | Gin + GORM | Gin + ent | GoFrame v2 + gdb |
| 优先级语义 | 数值**大**优先，严格分层 | 数值**小**优先；通用严格分层 / OpenAI 软因子 | 数值**大**优先，严格分层（v2） |
| 层内分配 | 加权随机（weight） | 通用 LRU；OpenAI Top-K 加权随机 | 加权随机 / Rendezvous 一致性哈希 |
| 重试计数 vs 优先级 | retry 当优先级层下标（耦合） | 完全解耦 | 完全解耦（excludeChannelIDs 独立） |
| 健康感知 | 仅 auto-ban（401 禁用） | **EWMA 错误率 + TTFT**，纳入评分 + 粘性逃逸 | **4 因子加权健康度**（成功率/延迟/稳定性/连续失败）+ 降权 + 自动禁用 |
| 亲和性定位 | 规则引擎（model/path/UA + KeySource），**为 prompt cache** | session hash + previous_response_id，**为对话 KV**，带健康度逃逸 | `tenant:user:apikey:model → channel`，Redis + 反向索引，**为路由稳定** |
| 亲和作用域 | 全局规则匹配 | 会话级（可跨优先级，带逃逸） | **仅最高优先级组内** |
| 重试上限 | `RetryTimes`（默认 **0**！） | 换号 **10**（Gemini 3）+ 同号 3 + HTTP 5 次/10s | **`maxRetries=3`**（4 次尝试） |
| 重试触发码 | 可配状态码范围（默认 4xx 除 400/408、5xx 除 504/524） | 401/403/429/529/≥500 换号 | 429/500/502/503/504 + 网络瞬时 |
| 流式安全 | 无特殊处理 | 流式已写禁止 failover | `ResponseWritten` 禁止重试 |
| 容量/并发控制 | 无显式 | 并发槽 + 等待队列 + wait plan | Redis 并发槽 + 租约刷新 |
| 跨实例稳定性 | 内存缓存（每实例独立） | 确定性种子 RNG | **Rendezvous 一致性哈希**（多实例对齐） |
| 非幂等保护 | 无 | 无显式 | **昂贵生成模糊送达不重试**（防重复计费） |
| 失败渠道处理 | auto-ban 移出缓存 | 临时封禁 + 换号 | 健康度降权 + 连续失败自动禁用 |

## 三、关键差异深度对比

### 1. 优先级模型：严格分层 vs 软因子

- **new-api / team-api**：严格分层——最高优先级组独占流量，层内才看权重/健康。设计简单、主备语义清晰。
- **sub2api（OpenAI 路径）**：优先级只是多维评分里的一个归一化因子，和负载/错误率/延迟平等竞争。更灵活（高优先级但高负载的渠道会被降级），但行为更难预测。
- **team-api 特点**：严格分层 + Rendezvous 哈希，是三者中**唯一原生支持多实例确定性选择**的（new-api 靠每实例内存缓存、sub2api 靠确定性种子，team-api 用一致性哈希更优雅）。

### 2. 健康感知：三者代际差异明显

- **new-api**：最粗糙——只有 401 auto-ban，无实时健康度。
- **team-api**：中间代——4 因子加权健康度 + EWMA 平滑 + 降权（不剔除）+ 连续失败自动禁用。粒度合理。
- **sub2api**：最精细——纯 EWMA（错误率 + TTFT）实时反馈，且**健康度参与粘性逃逸决策**（健康恶化主动跳船），这是 team-api 当前缺的能力。

### 3. 亲和性定位完全不同

- **new-api**：为 **prompt cache 命中**（绑定上游 KV 缓存），规则引擎匹配，全局生效。
- **sub2api**：为 **对话状态/KV**（订阅账户状态私有），会话级 + previous_response_id，**带健康度逃逸**。
- **team-api**：为 **路由稳定**（让同一租户/用户/key/模型尽量落同一渠道），简单直接，但**只限最高优先级组内**——若渠道分布在多优先级层，亲和效果会被优先级分层削弱。

### 4. 重试与 failover 的层次

- **new-api**：单层 `retry`，且默认 `RetryTimes=0`（不重试），耦合优先级层下标。
- **sub2api**：三层独立有界（同号 HTTP 5/10s → 同号业务 3 → 跨号 10），最细致，有流式安全阀。
- **team-api**：单层 `maxRetries=3`，但有三个优秀细节——容量溢出不消耗重试次数、`ResponseWritten` 禁止重试、昂贵非幂等生成的模糊送达不重试。整体介于 new-api 和 sub2api 之间。

## 四、team-api 现状评估与改进建议

### 现状评分

team-api 的调度实现**整体处于三者中游偏上**：
- ✅ **优于 new-api**：有真实健康度模型、响应已写安全阀、非幂等保护、跨实例一致性哈希、Redis 并发控制。
- ✅ **优于 sub2api**：多实例确定性（Rendezvous）、非幂等生成的重复计费保护。
- ⚠️ **弱于 sub2api**：缺粘性逃逸、重试层次单一、亲和受限于最高优先级组。
- ⚠️ **共性短板**：legacy/v2 双路径并存（`channel_scheduler_v2_enabled` 关闭时退化成纯优先级无健康度），需确保生产开 v2。

### 可落地的改进建议（按优先级）

| # | 建议 | 借鉴自 | 预期收益 |
|---|------|--------|---------|
| 1 | **亲和性加健康度逃逸**：亲和渠道 `HealthScore < 阈值` 时主动放弃亲和、降级选号，避免坏渠道粘死会话 | sub2api `shouldEscapeStickyAccount` | 防止一个故障渠道拖垮一批固定用户 |
| 2 | **亲和性作用域放宽**：允许亲和渠道跨优先级层命中（带降级权重），而非仅限最高优先级组 | sub2api 会话粘性跨优先级 | 提升亲和命中率，prompt cache/路由稳定收益更大 |
| 3 | **重试分层**：把「同渠道瞬时重试」与「跨渠道 failover」拆成两层独立计数，同渠道先短退避重试 1-2 次（429/503 常是瞬时的） | sub2api 三层 failover | 减少不必要的换渠道，降低抖动 |
| 4 | **健康度引入 TTFT**：在 4 因子里加首 token 延迟（流式场景比平均延迟更影响体感），或提高延迟权重 | sub2api EWMA TTFT | 流式体验优化 |
| 5 | **退避策略**：当前重试无退避（立即换渠道），高频 429 风暴下可能放大上游压力；加指数退避 | sub2api `retryBackoffDelay` / new-api | 保护上游、降低连环失败 |
| 6 | **下线 legacy 路径**：`channel_scheduler_v2_enabled` 关闭时退化为无健康度调度，建议确认生产已开并择机移除双路径 | — | 降低维护成本、避免误配置 |
