## 亲和性（Affinity）

### A1. 亲和命中绕过健康度降权 🔴
- **位置**：`relay/scheduler/scheduler.go:71-77`（`SelectStable` 直接返回亲和渠道）、`:185`（`effectiveWeight` 健康度降权）、`:83`（`highestPriorityCandidates` 仅剔除 `<20`）
- **现象**：`SelectStable` 一旦亲和渠道在最高优先级组内就**直接返回**，完全跳过 `effectiveWeight`。而候选过滤只剔除 `HealthScore < 20`。
- **后果**：一个亲和渠道健康度跌到 21 分（接近不健康），只要 ≥20，对该租户/用户/key/model 仍是 **100% 命中**，精心计算的健康度降权在亲和命中时**完全失效**。健康度体系与亲和性互相冲突。

### A2. 亲和仅在最高优先级组内生效 🟡
- **位置**：`relay/scheduler/scheduler.go:66-77`、`internal/logic/relay/provider.go:239-246`
- **现象**：`SelectStable` 先取最高优先级组，再在组内找亲和渠道；亲和渠道不在该组则被忽略，甚至被清除（`deleteAffinity`）。
- **后果**：用优先级做主备（如主=100、备=90）时，若亲和渠道是备，亲和直接失效。形成设计悖论——**优先级分层（failover）与亲和（粘性）无法同时生效**，亲和只在「不分层」时才工作。

### A3. 任何可重试错误都会清除亲和 🔴
- **位置**：`relay/handler/relay_handler.go:500`、`:565`
- **现象**：DoRequest / DoResponse 出错时**无条件**调用 `DeleteChannelAffinity`，哪怕只是瞬时 429/503 紧接着重试。
- **后果**：一次上游打嗝就毁掉积累多请求才建立的亲和绑定，下一个请求可能落到别的渠道重建亲和。**亲和反而成为路由中最不稳定的部分**，与其「路由稳定」目标相悖。

## 重试（Retry）

### R1. 重试无退避 🟡
- **位置**：`relay/handler/relay_handler.go:417`（`for attempt := 0; attempt <= maxRetries`）、`:502`、`:578+`（`continue`）
- **现象**：`maxRetries=3` 的重试循环失败后**立即** `continue` 换渠道，无 sleep / 指数退避。
- **后果**：上游 429 风暴时，瞬时把压力传导给剩余渠道，**放大对其他渠道和上游的冲击**，易引发连环失败。

### R2. 瞬时错误无原地重试，直接换渠道 🟡
- **位置**：`relay/handler/relay_handler.go:482-507`、`:525-577`
- **现象**：单层重试，不区分「同渠道瞬时重试」与「跨渠道 failover」。一个很可能 200ms 后就恢复的 503，会触发完整的「排除当前渠道 → 清亲和 → 重新选号 → 落到另一渠道」。
- **后果**：瞬时错误代价过高，**不必要的换渠道 + 亲和抖动**，且与 A3 叠加放大亲和失效。

## 健康度（Health）

### H1. 健康度更新为读-改-写，存在并发竞态 🔴
- **位置**：`internal/logic/relay/health.go:30-33`（读）、`:40-43` / `:70-76`（基于读值计算）、`:54-63` / `:81-88`（写）
- **现象**：`UpdateHealthScore` 先 `Scan` 读出 `success_rate/consecutive_failures` 等字段，在 Go 内基于读值算出新值，再 `Update` 写回。无行锁、无原子表达式（如 `success_rate = success_rate * 0.9`）、无版本号。
- **后果**：同一渠道并发失败时**丢失更新（last-write-wins）**——EWMA 平滑失真、`consecutive_failures` 被少计（N 个并发失败各读到同一旧值、各写 +1，最终只 +1 而非 +N）。健康度数值在并发下不准确，影响降权与自动禁用判定。

### H2. 失败路径同步写健康度，阻塞重试 🟡
- **位置**：`relay/handler/relay_handler.go:497`、`:559`（失败分支直接调用 `UpdateChannelHealth`）；`internal/logic/relay/health.go:22`（同步 Scan + Update）
- **现象**：失败时在重试热路径里同步执行一次「读 + 写」DB 操作（带 30s 超时 settleCtx），写完才能进入下一次重试。
- **后果**：每次失败的重试都要**等一次 DB 往返**，拖慢错误处理与 failover；高并发 + 多渠道连续失败时延迟累积。（对比：成功路径用 `postCtx` 异步化，失败路径没有。）

## 性能（Performance）

### P1. 选号无渠道池内存缓存，每次重试重查 DB 🟡
- **位置**：`internal/logic/relay/provider.go:135-156`（`selectChannelFromDB` 每次执行 3 表 JOIN `Scan`）、`relay/handler/relay_handler.go:418`（每次 attempt 都调用）
- **现象**：`selectChannelFromDB` 每次都跑 `chn_abilities JOIN chn_channels JOIN chn_health_scores` 的 SQL，且每次重试（最多 4 次/请求）都重选一次。未发现上游有渠道池的内存缓存。
- **后果**：单请求最多 4 次 DB 查询，高 QPS 下成为**数据库热点**。

## 运维（Operations）

### O1. legacy / v2 双路径并存，关闭时退化为无健康度 🔴
- **位置**：`internal/logic/relay/provider.go:162`（`channel_scheduler_v2_enabled` 开关）、`:163-195`（legacy 分支）、`:191`（`HealthScore: 100` 硬编码）
- **现象**：开关关闭时走 legacy 路径——仅按 `priority DESC, weight DESC` 排序取首个有 key 的渠道，且 `HealthScore` 写死为 `100`。
- **后果**：一旦误关闭开关，**健康度感知调度被静默关闭**，所有渠道被视为满分健康，退化为主备轮询。存在配置误操作风险，且双路径增加维护成本。

## 能力局限（Limitations）

### L2. 无「优先级溢出分流」能力 ⚪
- **位置**：`relay/scheduler/scheduler.go:83-106`（`highestPriorityCandidates` 只取最高优先级组）、`:109-137`（`groupByPriority`）
- **现象**：调度只有两档语义——最高优先级组**独占**全部流量，或同优先级组内按权重分流。不存在「高优先级渠道负载满了/并发占满后，溢出到低优先级渠道」的能力。
- **后果**：无法表达「优先用 A，A 扛不住时自动分一部分给 B」这类**优先级 + 溢出**的混合策略。多优先级渠道只能做冷备（见 [`channel-scheduling-comparison.md`](./channel-scheduling-comparison.md)），低优先级渠道容量在主渠道健康时完全闲置。

### L3. 亲和无会话 / 对话维度 ⚪
- **位置**：`internal/logic/relay/affinity.go:17-21`（`affinityIdentity` 仅含 `tenantID:userID:apiKeyID:modelName`）
- **现象**：亲和键是「租户 + 用户 + API Key + 模型」四元组，不包含会话 ID / 对话 ID / previous_response_id。
- **后果**：只能做**身份级粘性**，无法做**会话级粘性**——同一用户+key+模型的多段独立对话都强制路由到同一渠道；反过来也无法保证「同一段多轮对话」落在同一渠道（从而无法稳定命中上游 KV / prompt 缓存）。
