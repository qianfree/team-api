## 1. 体系速览

一次请求的调度路径：**会话键解析 → 目录快照（内存）→ 绑定守卫 → 加权 HRW 选择 → 凭证选取 → 容量租约 → 转发 → 错误分类 + FSM 重试 → 结果回写（健康 EWMA / 熔断 / 绑定续期）**。

| 组件 | 位置 | 说明 |
|---|---|---|
| 调度核心（纯函数） | `relaykit/dispatch/` | 权重合成、HRW、重试 FSM、熔断状态机；无 I/O，可单测 |
| 适配层 | `internal/logic/dispatchadapter/` | 目录快照、Redis Lua 状态、策略加载、降级、维护 cron |
| 运行时状态 | Redis `dispatch:v1:*` | 绑定/健康/熔断/租约/凭证冷却/429 水位，全部 Lua 原子 |
| 快照落盘 | `chn_health_scores` | 每 5min 由维护 cron 从 Redis 落盘，**仅供仪表盘**，调度不读 |
| 指标 | `ops_system_metrics`（metric_type=channel_dispatch） | 每分钟累计计数快照，相邻行做差得速率 |

### 权重公式（每渠道）

```
W = weight × tierFactor × healthFactor × headroom^γ × costFactor × rampFactor
```

- **tier**（渠道表单「调度层级」）：primary=1.0 / secondary=0.15 / reserve=0.02（policy 可调）。备用层平时承接零星流量＝天然保温探活。
- **healthFactor** = succEwma^α × 延迟惩罚。succEwma 按错误类别分档衰减：瞬时/超时 ×0.93、429 ×0.97、致命 ×0.70；客户端错误与凭证错误**不计**渠道健康。
- **headroom**：softLimit 来自手动 `max_concurrency`，未配置时按 429 起始水位自动估计 `max(4, floor(onset×0.9))`。
- **costFactor**：`chn_abilities.cost_ratio`（上游价/基准价），越便宜权重越高（温和优势，不碾压健康信号）。
- **rampFactor**：熔断恢复 / 手动启用 / 新建渠道后 2 分钟内从 5% 爬坡到 100%。

## 2. 路由策略（channel_routing_policy）

存于 `sys_options`，key = `channel_routing_policy`，JSON 浅覆盖默认值，**30s 内热生效，无需重启**。可在**管理后台 → 系统设置 → 渠道 → 路由策略覆盖（JSON）**中编辑，保存时校验 JSON 合法性与取值范围，非法配置拒绝入库；调度侧加载仍会二次校验（失败沿用上一份）。完整字段与默认值见基线方案 §12 + 开发计划 §4.3。

**租户级覆盖**：key = `channel_routing_policy:tenant:<租户ID>`（同样存 `sys_options`），三层浅合并：内置默认 → 全局覆盖 → 租户覆盖。租户覆盖非法时告警并回落全局策略，不影响该租户请求；解析结果本地缓存 30s。暂无管理界面，由 SQL 管理：

```sql
INSERT INTO sys_options ("key", value, category, description, is_public)
VALUES ('channel_routing_policy:tenant:123', '{"retry":{"failoverBudget":3}}', 'channel', '租户123路由策略覆盖', false)
ON CONFLICT ("key") DO UPDATE SET value = EXCLUDED.value;
```

常用调参场景：

| 想要的效果 | 改什么 |
|---|---|
| 备用渠道多接/少接平时流量 | `tierFactors.secondary`（默认 0.15；0=纯冷备，靠扩组兜底） |
| 溢出更早/更晚发生 | `load.gamma`（默认 2；调大→接近饱和才坍缩更快） |
| 会话粘性更持久 | `binding.ttlSeconds`（默认 1800，成功滑动续期） |
| 病渠道上的会话更快迁走 | `binding.keepHealthMin`（默认 0.5，healthFactor 低于即重绑） |
| 更激进/保守的原地重试 | `retry.inPlaceBudget`（默认 2）、`retry.backoffBaseMs` |
| 熔断更灵敏/迟钝 | `breaker.failThreshold`（60s 窗口默认 8 次） |
| 图片/视频允许有限重试 | `retry.unsafeFailoverBudget`（默认 0；仅"确定未送达"时生效） |
| 调整哪些端点算非幂等 | `replay.unsafeModes` / `replay.safeModes`（relay mode 字符串，默认 unsafe=images_generations/images_edits/video_generations） |

示例（把备用层调成纯冷备 + 熔断更灵敏）：

```json
{"tierFactors": {"primary": 1.0, "secondary": 0, "reserve": 0}, "breaker": {"failThreshold": 5}}
```

## 3. 排障手册

### 3.1 某渠道突然没有流量

按顺序检查：

1. **熔断了？** Redis：`HGETALL dispatch:v1:breaker:<渠道ID>`。`state=1` 为 OPEN；`opened_ms`+`cooldown_ms` 决定何时进入探测。指标 `breaker_opens` 有计数。
2. **被自动禁用？** 渠道状态为 disabled 且 `auto_disabled=1` → 熔断持续超 10 分钟被自动禁用（开关 `channel_auto_disable_enabled`）。有全租户通知与 `[Dispatch] 渠道 X 熔断持续...已自动禁用` 日志。开启「自动恢复探测」后测试通过会自动回归（回归后自动进入爬坡）。
3. **权重被压到 0？** 看渠道日志 `ForwardingTrace.scheduler[].weights`：base=0（权重配 0）？headroom=0（inflight 打满 softLimit，查 `ZCARD dispatch:v1:inflight:<ID>`）？tier=0（层级因子配 0）？
4. **Key 全部冷却？** 401/403 会冷却对应 Key 5 分钟：`EXISTS dispatch:v1:credcd:<keyID>`。全部 Key 冷却期间该渠道整体不可用（trace 中 excluded_request 计数）。

### 3.2 会话为什么换渠道了（粘性丢失）

绑定失效只有三种途径：TTL 过期、守卫不合格（被绑渠道 healthFactor < 0.5 或原始余量 < 0.1 或熔断）、渠道被禁用/删除时批量清理。**单次请求失败不清绑定**。排查：渠道日志 `scheduler[].reason`——`bind`=命中，`hrw`=新绑定/重绑，`overflow`=高层级在场但饱和。会话键来源看 `session_source`（hdr/anthropic/openai/ident）。

### 3.3 溢出没按预期发生 / 发生得太多

- 没溢出：primary 未配 `max_concurrency` 且从未吃过 429 → 无容量信息，headroom 恒为 1。配手动上限或等 429 估计器收敛（`HGET dispatch:v1:limit429:<ID> onset_ewma`）。
- 溢出过多：检查 primary 健康（healthFactor 低同样压权重）；`overflow_by_tier` 指标看流向。

### 3.4 Redis 故障时会发生什么

按基线方案 §13 + 修订 R4 降级，**服务不中断**：绑定退化为纯 HRW（软粘性仍在）、熔断退化为实例本地、健康用最近快照；容量默认 fail-open，**勾选「严格容量」的渠道 fail-closed**（实例限额 = `max_concurrency / degrade.maxReplicas`，未配上限的严格渠道降级期间直接不可用——这是刻意行为）。多副本部署务必把 `degrade.maxReplicas` 配成实际副本数。

### 3.5 502 风暴 / 401 / 504 的预期行为

| 现象 | 预期行为 |
|---|---|
| 上游 502/503 抖动 | 同渠道退避重试（100ms→200ms+jitter，预算 2），多数请求无感消化，不换渠道不丢缓存 |
| 单 Key 401 | Key 冷却 5min；渠道有备用 Key → 轮换后继续；唯一 Key → 该渠道致命，熔断直达 + failover |
| 504 | 不原地重试；文本请求 failover，图片/视频终止（防重复生成） |
| 流已开始后中断 | 必终止（防响应污染），按流中断结算 |

## 4. 客户端接入：X-Session-Id

会话级粘性的最优信号是显式头：

```
X-Session-Id: <你的会话唯一标识，≤256 字节，无控制字符>
```

同一值的请求会稳定路由到同一渠道（命中上游 prompt 缓存）。未携带时按协议信号回退：Anthropic `metadata.user_id`（Claude Code 自动携带，含 session 段）→ OpenAI `previous_response_id`/`conversation_id` → 身份四元组（租户+用户+Key+模型）。平台自有 SDK 应默认携带此头。

## 5. 遗留与冻结项

- `chn_channels.priority`：列保留但**不再参与调度**（迁移 000014 起由 tier 三档替代），仅供历史查询与回滚。
- `chn_channel_affinities` 表：已废弃（迁移 000015 标记），绑定只存 Redis。
- 旧开关 `channel_scheduler_v2_enabled` / `channel_affinity_enabled(_ttl_seconds)` / `channel_capacity_enabled` / `channel_dispatch_shadow_enabled` / `channel_auto_disable_threshold`：已从设置注册表退役（sys_options 中的历史行无害，管理界面不再展示）。
- `channel_auto_disable_enabled` 保留，语义改为「熔断持续超过 `breaker.autoDisableAfterSeconds` 自动禁用」。
