## 2. 对基线方案的修订清单（Delta）

实现时以基线方案为蓝本，叠加以下 7 项修订。修订编号在后续任务分解中引用。

### R1. 凭证级归因与轮换（来自 gpt §11.3/11.4）

现状：`getChannelKey(ctx, channelID)` 每渠道只取第一条 active Key（`internal/logic/relay/provider.go:1071`，注释明确"每渠道仅一个 Key"），**当前不存在轮换能力**，属新增：

- 错误分类新增 `ErrClassCredential`：401/403 以及可识别的"Key 额度耗尽"错误**先归因到凭证**，不再直接定为 CHANNEL_FATAL。
- 处理流程：凭证错误 → 该 KeyID 写入 Redis 冷却（`dispatch:v1:credcd:<keyID>`，TTL 默认 300s）→ 同渠道选下一个未冷却的 active Key 重试一次（**凭证轮换预算 = 1/渠道/请求**，独立于原地/failover 预算）→ 该渠道全部 Key 冷却或耗尽 → 升级为 CHANNEL_FATAL（走基线方案的熔断 + 告警）。
- 链路改造：`common.ChannelSelection` 增加 `KeyID int64` 字段；新增 `getChannelKeyExcluding(ctx, channelID, excludeKeyIDs)`（按 id 稳定排序取首个未排除的 active Key，复用现有解密与 OAuth 刷新逻辑）；`Outcome` 上报带 KeyID，凭证失败**不计入渠道健康 EWMA**（只计凭证冷却），避免一个坏 Key 拉低整条渠道健康分。
- 只有一个 Key 的渠道（当前全部渠道的实际形态）：轮换预算天然用不上，行为退化为「凭证错误 → 冷却唯一 Key → 升级 CHANNEL_FATAL」，与基线方案一致，无兼容性风险。

### R2. 可重放性与送达状态（来自 gpt §6.1/§11.2）

- 新增两个纯类型（放核心库 `types.go`）：
  - `Replayability`：`ReplaySafe`（查询/embedding/rerank）、`ReplayCostly`（chat/completion 文本生成）、`ReplayUnsafe`（图片/视频生成、异步任务提交）。由 relay mode 静态映射，做成可配置表。
  - `DeliveryState`：`NotSent`（连接失败/请求体未发出）、`MaybeSent`（写出后连接重置/读超时/EOF）、`ResponseReceived`、`ResponseStarted`（已向客户端写出字节）。由执行器（handler）在错误发生点标注。
- 硬规则（进重试 FSM，优先级高于错误分类）：
  - `ReplayUnsafe + MaybeSent` → **无条件 Abort**，无论状态码；
  - `ResponseStarted` → Abort（等价基线方案 PARTIAL_STREAM，统一到 DeliveryState 表达）；
  - `ReplayUnsafe` 的原地/failover 预算默认收紧为 0/0（可配），只有 `NotSent` 允许 failover。

### R3. 504 从 TRANSIENT 拆出（来自 gpt §11.4）

基线方案将 502/504 同归 TRANSIENT。修订为：

- **502、520-527、请求未发出的连接重置**：维持 TRANSIENT，原地退避重试；
- **504**：默认**不原地重试**（网关超时意味着请求大概率已送达且上游处理慢，原地重试大概率再超时），按 `Replayability` 决定：`ReplaySafe/Costly + 未写出响应` → 直接 failover；`ReplayUnsafe` → Abort。归类并入 TIMEOUT 处理分支。

### R4. 昂贵渠道 Redis 故障 fail-closed（来自 gpt §15.3）

基线方案 Redis 故障时容量一律 fail-open。修订为按渠道可配：

- `chn_channels` 新增 `strict_capacity BOOLEAN DEFAULT FALSE`（并入迁移 000014）。
- `strict_capacity=true` 的渠道在 Redis 不可用时使用实例级保守限额：`localLimit = max(1, floor(max_concurrency / 部署副本数))`，副本数从配置读（`manifest/config`，默认 1）；未配 `max_concurrency` 的 strict 渠道降级期间直接排除。
- 默认 false（fail-open），仅对高成本/严格配额渠道由运营手动开启。

### R5. 决策观测并入 ForwardingTrace（来自 glm §11）

基线方案 §14.1 的决策日志（weight_breakdown、binding 命中、排除原因）除写 DEBUG 日志外，**同步挂到现有 `relay/common.ForwardingTrace`**，随现有渠道日志链路展示，不新建日志通道。字段命名对齐基线方案 §14。

### R6. 健康 EWMA 按错误类别加权（来自 glm §5.2 errorDistScore 思想，简化版）

基线方案失败一律 `succ = succ × 0.9`。修订为衰减系数按错误类别分档（Lua 脚本 ARGV 传入）：

- TRANSIENT / TIMEOUT：×0.93（轻罚，瞬时抖动不重伤）
- RATE_LIMIT：×0.97（429 主要喂 softLimit 估计器，基本不伤健康）
- CHANNEL_FATAL：×0.70（重罚，加速权重坍缩）
- CLIENT / Credential / 客户端取消：**不上报健康**（gpt §12.1 原则：请求级错误与凭证错误不得计入渠道失败率）

### R7. relaykit 分支适配

- **核心库落点改为 `relaykit/dispatch/`**（替代基线方案的 `relay/dispatch/`）：relaykit 是独立无 gf 依赖的 module，纯度由模块边界 + 编译器强制，阶段 0「import 无 gf/dao/redis」验收自动成立；且错误分类器可自然 import 同 module 的 `relaykit/types`。
- 错误分类器签名扩展：`Classify(statusCode int, err error, delivery DeliveryState, retryAfter time.Duration) ErrorClass`，内部解包 `relaykit/types.NewAPIError`——尊重 `IsSkipRetryError`（→ 直接 Abort 或 Failover，不原地重试）、`IsChannelError`（→ 渠道级归因），按 ErrorCode 细分凭证类错误。
- 提交前缀约定：调度重构的提交统一用 `feat(dispatch): ...` / `test(dispatch): ...`，与本分支 relaykit 提交（`feat(relaykit):`）区分，便于将来按需 cherry-pick 或回滚。

## 3. 最终模块结构

```
relaykit/dispatch/                    ← 新增。纯库（module 边界强制无 gf/dao/redis）
    types.go        Channel、Tier、RequestProfile、Decision、Outcome、ScoredChannel、
                    Replayability、DeliveryState（R2）
    session.go      会话键解析链（纯函数）
    classify.go     错误分类器（含 NewAPIError 解包 R7、ErrClassCredential R1、504 特判 R3）
    score.go        W(c) 权重合成（纯函数）
    hrw.go          加权 rendezvous 选择（纯函数）
    policy.go       重试决策 FSM（含凭证轮换预算 R1、重放硬规则 R2）+ 策略结构体
    breaker.go      熔断状态机（纯函数 + 端口）
    coordinator.go  编排（Route/Next/Report/Finish）
    ports.go        CatalogPort / StatePort / Clock

internal/logic/dispatchadapter/       ← 新增。适配层，全部 I/O
    catalog.go      三表 JOIN → 内存快照（5s 刷新 + pub/sub 失效），含 Key 列表快照（R1）
    state_redis.go  StatePort Redis 实现（基线方案 §10 Lua + credcd 冷却 R1 + 分档衰减 R6）
    state_local.go  Redis 降级镜像（含 strict_capacity 保守限额 R4）
    config.go       routing policy 加载/校验/热更新
    wire.go         组装 coordinator

relay/handler/relay_handler.go        ← 阶段 3 重写重试循环（Route/Next/Report/Finish）
internal/logic/relay/                 ← 阶段 3 起逐步退役调度部分；渠道 Key 解密/OAuth 刷新逻辑保留复用
relay/scheduler/                      ← 阶段 5 删除
```

依赖方向：`relay/handler → relaykit/dispatch ← internal/logic/dispatchadapter`。

## 5. 分阶段开发计划

> 原则沿用基线方案 §16：每阶段独立可合入、可回滚；不引入长期存活的新旧切换开关；灰度用影子模式，切换一次性完成后立即删旧码。全部在 `feat/relaykit-migration` 分支进行，提交前缀 `feat(dispatch)`。
> 测试命令注意：跑覆盖率需 `GOTOOLCHAIN=go1.25.8 go test -cover ...`（工具链已知问题）；relaykit 子 module 内需 `cd relaykit` 后执行。

### 阶段 0：纯核心库（零接线，零风险）｜预估 4~6 人日

**前置任务（可并行）**
- [ ] 抓包验证 Claude Code `metadata.user_id` 格式（`session_<uuid>` 段是否稳定），结论回写基线方案 §19.1。验证失败不阻塞——解析链自动降级身份级。

**开发任务**
- [ ] `relaykit/dispatch/types.go`：全部领域类型，含 `Replayability`/`DeliveryState`（R2）、`Decision.KeyID`（R1）
- [ ] `session.go`：解析链（X-Session-Id → anthropic metadata → openai responses → 身份四元组），按基线方案 §3
- [ ] `classify.go`：错误分类表（R1 ErrClassCredential、R3 504 拆出、R7 NewAPIError 解包）
- [ ] `score.go` + `hrw.go`：权重合成 + HRW，按基线方案 §4/§5.1
- [ ] `policy.go`：重试 FSM——三预算（原地/凭证轮换/failover）+ R2 硬规则 + 退避曲线；策略结构体含 §4.3 新字段
- [ ] `breaker.go`：熔断状态机，按基线方案 §7
- [ ] `coordinator.go` + `ports.go`：Route/Next/Report/Finish 编排（Next 返回的 Decision 含渠道+KeyID；凭证轮换时 Next 返回同渠道新 Key）

**单元测试清单**（表驱动为主，补 gpt 式属性测试）
- [ ] HRW 分布（10 万采样，权重比例误差 < 2%）；同 seed 万次同结果；分数并列按 ChannelID 稳定
- [ ] 会话键解析全 case（含抓包真实样本、超长/非法值拒绝）
- [ ] 错误分类全表覆盖（含 NewAPIError SkipRetry/ChannelError 路径、504、凭证错误）
- [ ] FSM 全路径：三预算独立扣减；`ReplayUnsafe+MaybeSent` 任意状态码必 Abort；`ResponseStarted` 必 Abort；凭证轮换耗尽升级 CHANNEL_FATAL；Retry-After 遵从
- [ ] 属性测试：任意错误序列不突破预算；候选顺序打乱不改变选择结果；禁用渠道永不返回
- [ ] 熔断全转移路径（cooldown 指数递增、探测窗口）
- [ ] 权重边界（headroom=0、health=0.01、tierFactor=0、costFactor clamp）
- [ ] 绑定守卫防抖（模拟 headroom 抖动，重绑次数 ≤ 阈值；**溢出到 secondary 的绑定在守卫下保持稳定**——glm 缺陷的回归用例）

| 2 | 与 relaykit 工作流同分支同文件（relay_handler.go） | 提交前缀隔离；阶段 3 动工前对齐；调度侧后合 |
| 3 | tierFactor/γ/衰减分档等参数初值偏差 | 影子模式 weight_breakdown 校准；全部热更新，无需发版 |
| 4 | 429 自动估计冷启动 | 可接受（429 触发 failover 用户无感）；敏感渠道手动配 max_concurrency |
