# 渠道调度三方案对比评审

> 评审对象：[`claude设计的渠道调度方案.md`](./claude设计的渠道调度方案.md)、[`glm设计的渠道调度方案.md`](./glm设计的渠道调度方案.md)、[`gpt设计的渠道调度方案.md`](./gpt设计的渠道调度方案.md)
> 评判基准：[`当前渠道调度存在的问题.md`](./当前渠道调度存在的问题.md) 的 11 个问题（A1-A3 / R1-R2 / H1-H2 / P1 / O1 / L2-L3）+ 项目 memory 中已锁定的 4 个决策（Redis 真相源、成本感知开启、不做对话指纹、自然探活）。
> 评审时间：2026-07-30。状态：待讨论。

## 一、结论（TL;DR）

**claude 方案整体最优，建议以它为实施主干，合入 gpt 方案的 2~3 个关键补强；glm 方案关闭归档。**

三份方案核心骨架高度趋同（都遵守已锁定决策：加权 Rendezvous Hash 选择、粘性作为涌现属性、Redis Lua 原子状态、错误分类 + 双预算重试、自然探活熔断、纯函数核心 + 端口适配层）。差距在完成度、对本项目的贴合度、边界处理：

- **claude**：最自洽、最贴合本项目、可直接开工，但缺凭证级归因和非幂等重放保护；
- **gpt**：工程严谨性和运维可控性最强，但范围严重膨胀、偏通用方案，且**漏掉了成本感知因子（违反已锁定决策 2）**；
- **glm**：三份中最薄，且绑定守卫（keepThreshold）存在真实设计缺陷，有效内容被 claude 方案完全覆盖。

## 三、各方案关键硬伤

### glm：绑定守卫存在真实设计缺陷

守卫判据是 `有效权重 ≥ keepThreshold = 0.3 × baseWeight`（§3.3），而有效权重包含 `tierBias`。备用渠道 tierBias 默认 0.1，意味着：

> **溢出到备用渠道建立的绑定，下一个请求必然不满足守卫条件**（0.1 × base < 0.3 × base）。持续高压期间，备用渠道上的会话每次请求都重绑、永远粘不住，上游 KV/prompt 缓存收益归零——而「保缓存」正是亲和的存在意义。

对照组：claude 的守卫判据是被绑渠道自身状态（熔断非 OPEN、healthFactor ≥ 0.5、headroom ≥ 0.1，§5.2），与 tier 和成本解耦，不存在此问题；gpt 用显式逃逸条件（压力 < 0.90 等，§7.5），也没有此问题。

除此之外 glm 整体最薄：无请求全景图、无迁移 SQL、Lua 有伪码、开放问题最多。它更像已锁定决策的「基线展开版」，全部有效内容被 claude 方案严格覆盖。

### gpt：漏掉成本感知 + 范围膨胀

1. **违反已锁定决策 2**：§9.6 `effectiveWeight = baseWeight × healthFactor × capacityHeadroom × recoveryRamp × temporaryMultiplier`，没有 costFactor。成本只作为观测口径（cost_share），不参与调度。
2. **范围膨胀**：临时流量策略、模拟器、RBAC、双人审批、审计表等控制面能力占全文近一半，把「修复 11 个调度问题」的重构变成 8 阶段平台工程；首个产生业务价值的阶段（阶段 4 接管选择）来得很晚。
3. **通用性代价**：`sched_` 表前缀不符合项目前缀规范，无 goose 编号，不引用现有代码，落地前需要一轮完整的「翻译」。
4. 对 Claude Code 会话识别一刀切放弃，相比 claude「解析 + 验证 + 监控 + 优雅降级」的处理方式，工程上保守过头。

### claude：两个真实缺口（恰是 gpt 的强项）

1. **无凭证级错误归因**。本项目有 `chn_channel_keys` 表（一渠道多 Key），claude 把 401/403 直接定为 CHANNEL_FATAL 并熔断整条渠道（§6.1）——**一个 Key 失效会误杀整条渠道**。gpt 的做法正确：401 先归因凭证、同渠道轮换一次、全部凭证失败才升级渠道级（§11.3/11.4）。
2. **非幂等请求重放保护不完整**。本项目有 taskchannel（kling/midjourney/sora/suno），图片/视频/异步任务重试可能重复扣费、重复出任务。claude 只有 PARTIAL_STREAM 一档，缺 gpt 的 `ReplayUnsafe + DeliveryMaybeSent → 必须停止` 语义（§6.1/§11.2）。

补充两个由此新增的合并候选项（并入第四节修订清单讨论）：

- **504 处理改从 gpt**：将 HTTP 504 从 claude 的 TRANSIENT 类中拆出，默认不原地重试，仅对可重放且未输出响应的请求允许受限 failover；
- **昂贵渠道 fail-closed 选项**：claude §13 的容量降级从"一律 fail-open"改为按渠道可配（参考 gpt §15.3），Redis 故障时严格容量/高成本渠道使用实例级保守限额。

### 6.0 已议定：固定三档 vs 数值优先级（2026-07-30 讨论）

质疑：三档（首选/备用/保底）最初只是需求方随口提议，是否数值优先级更好？

**结论：维持固定三档。** 论证要点：

1. 老 `priority` 数值实际身兼四职（先后序、分流比、成本偏好、灾备），其隐含的「同值=同组独占」语义正是 A2/L2 的根源。新权重模型把这些职责拆给正交因子（weight / costFactor / healthFactor / headroom），tier 剩下的唯一语义「策略偏好分层」天然只有约三档粒度（new-api 的数值优先级实践也自发收敛为少数档位）。
2. 新模型无硬分组，数值优先级必须映射为连续权重因子 `f(priority)`，任何映射曲线都让「差 1 分 vs 差 20 分」的行为不可预测——等于换个形式带回 A2 的模糊性。固定三档的因子刻意拉开数量级（1.0/0.15/0.02），档间行为可预测、可穷举测试。gpt 的角色分层模型下数值优先级更不可行（阈值状态机随档位数相乘）。
3. 数值灵活性未丢失：档位因子在 routing policy 中可配可热更；档内精细分配靠保留的 `weight`；将来加第四档 = 一个枚举值 + 一条 tierFactors 配置（tier 为 VARCHAR 列，priority 列冻结可回滚）。
4. 数值唯一独有的表达力——多渠道严格串行偏好序（A>B>C>D>E）——在网关场景是反模式：多数是成本序/可靠性序的误表达，且意味着多渠道长期全闲置（即最初抱怨的「备用永不被请求」的加强版）。
5. 警惕的折中方案：「数值优先级 → 连续因子映射」看似兼得，实为最差选择（见第 2 点）。

1. claude §19.1 的 `metadata.user_id` 格式验证需在阶段 0 前完成抓包确认（gpt 的质疑提醒了该风险确实存在，但正确响应是验证而非放弃）。
2. 成本因子的挂载粒度：claude 挂 `chn_abilities.cost_ratio`（渠道×模型，无量纲比例），glm 挂 `chn_channels`（渠道级单价 decimal）。**倾向 claude 的做法**——粒度更细，且无量纲比例天然回避币种/汇率问题，也不落入资金字段的 decimal 强约束范围。
3. 凭证级归因（修订 1）会触碰 claude 方案的熔断粒度设计（渠道级 + 渠道×模型级），可能需要补充「凭证级冷却」状态，实现前需细化。
