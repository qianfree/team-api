# JS 任务插件 API v1

面向插件作者的唯一接口规范。配套交付：`internal/jsplugin/contract/v1.d.ts`（TS 类型，IDE 补全）与作者模板 golden 参考实现（`internal/jsplugin/template/plugin.js`，非内置实例）及内置插件（`internal/jsplugin/builtin/`：alibaba/doubao/hailuo/teamapi 真实实现）。以 Go 侧 `internal/jsplugin/contract` 为事实源，不一致以代码校验为准。

**内置与上传**：插件分两类来源——内置（go:embed 随二进制，管理端可见标记「内置」，不可删除）与上传（管理端上传 plugin.js）。上传版本激活即覆盖同 key 内置版本，删除上传版本后自动回落内置。分发格式与契约对两类完全一致。

**验收一句话**：照 golden 插件起步，删掉不需要的钩子，上传即被校验——不读基座代码也能写对。

---

## 1. 心智模型：一次任务的完整生命周期

```
客户端 ──── 基座 ──────────────── 插件(JS) ──────── 上游厂商
  │  POST /pjs/{key}/submit/music
  ├─→ 分发器匹配路由 → ① decodeRequest ──→  "这是什么请求？什么模型？"
  │            ←─ {kind:"submit", model, requestBody}
  │  选渠道（基座，按 plugin_key + 模型映射定上游名）
  ├──────────────────────────── ①′ validateRequest（可选）→ "按上游型号校验/修正请求"
  │            ←─ {requestBody?}
  │  查定价·预扣（基座）
  ├──────────────────────────── ② buildSubmitRequest → "怎么调上游？"
  │            ←─ {url, method, headers, body}
  │  ══ 基座发起上游请求（Authorization 由基座注入渠道密钥）══
  │            ←─ ③ parseSubmitResponse ←─ "受理了吗？任务ID？"
  │            ←─ {taskId, taskData, state}
  │  落库（task_xxx），按 ④ renderSubmit（可选）渲染响应
  │
  │  ⏰ 每轮轮询（基座 15s 循环）：
  │            ←─ ⑤ buildQueryRequest → "怎么查进度？"
  │            ←─ ⑥ parseQueryResponse ←─ "完了吗？"
  │            ←─ {items:[{taskId, done, progress?, taskData, state, usage?, artifacts?, error?}]}
  │  终态：结算（基座，按官方 usage 多退少补）→ 产物处理
  │
  │  GET /pjs/{key}/fetch/:task_id
  ├─→ ⑦ renderTask（可选）→ "给客户端看什么格式？"（缺省=透传任务字段）
```

**必选五钩子**（最小任务插件）：`decodeRequest`、`buildSubmitRequest`、`parseSubmitResponse`、`buildQueryRequest`、`parseQueryResponse`。可选：`validateRequest`、`estimateUsage`、`renderSubmit`、`renderTask`。

## 2. manifest（`export const meta`）

```js
export const meta = {
  apiVersion: 1,
  key: "golden",                  // 小写字母开头，[a-z0-9-]，2-30
  name: "Golden 示例插件",
  version: "1.0.0",               // semver；同版本号不允许改源码（hash 锁定）
  models: ["golden_music", "golden_video"],  // 插件支持的上游模型名（见下方「模型名语义」）；跨插件可重名；视频模型需配合 standardVideos 声明（见 golden 模板）
  fetchMode: "per_task",          // per_task（默认）| batch（同渠道整批一次上游往返）
  allowedHosts: [],               // utils.fetch 额外白名单：host 或 host:port
  config: [                       // 插件配置项（管理端动态表单，加密字段掩码存储）
    { key: "api_key", label: "厂商密钥", type: "string", encrypted: true },
    { key: "max_clips", label: "单次上限", type: "int", default: 4, halfWidth: true },
  ],
  // routes（可选，与 standardVideos 至少声明其一）：纯标准端点插件（仅经 /v1/videos、
  // /v1/video/generations 提交，不暴露 /pjs 原生入口）可整体省略 routes，连同
  // decodeRequest / renderSubmit / renderTask 等原生路由专属钩子——标准端点响应由平台渲染
  routes: [
    { method: "POST", path: "/submit/:action", type: "submit" },
    { method: "GET",  path: "/fetch/:task_id",  type: "query" },
    // dynamic（可选）：一型两用——解码结果定走向（suno 式 POST /fetch 批量查询）
    // { method: "POST", path: "/fetch", type: "dynamic", decode: "decodeBatch" },
  ],
  // standardVideos（可选）：标准视频端点解码钩子名——声明后模型可经 /v1/videos 与
  // /v1/video/generations 提交（通用任务体 → 原生 requestBody 的映射由该钩子完成）
  // standardVideos: "decodeVideos",
  // referenceRoles（可选）：decodeVideos 能承接的参考素材角色（通用任务体 references[].role）。
  // 宿主在调用 decodeVideos 前拦截未声明的角色（返回 reference_not_supported，不静默丢弃）；
  // 缺省 = 仅 first_frame（只认单张首帧图）
  // referenceRoles: ["first_frame", "last_frame", "reference_image", "reference_video", "reference_audio", "file", "link"],
  // modelsFromConfig（可选）：扩展上游模型承载配置键——该 config 键的值（换行/逗号分隔
  // 或 JSON 数组）运行时并入支持清单，上游新增模型在管理后台改配置即可，无需改
  // 插件源码重新上传
  // modelsFromConfig: "extra_models",
};
```

- 路由实际地址 = `/pjs/{key}` + path；`:param` 段进入钩子的 `ctx.params`；
- **query 路由**是客户端查询单个任务的入口：**必须带路径参数**（如 `/fetch/:task_id`，值为平台公开任务 ID `task_xxx`），基座读库后调 `renderTask` 回包——不调上游、不调 `buildQueryRequest`（那是后台轮询用的）；查询串（`?id=`）读不到，上游用查询串的厂商也声明成路径参数形态。任务进度由基座后台轮询（`buildQueryRequest` → `parseQueryResponse`）推进，与 query 路由无关；
- 同插件内 `method + 路径形状` 唯一；**跨插件路由不做冲突约束**——`/pjs/{key}` 命名空间天然隔离（分发器先按 URL key 定位插件、再在插件内匹配路由），各厂商兼容的同名路由形态（如 `GET /videos/:task_id`）可在多个插件中并存；
- **模型名语义（`meta.models` = 支持的上游模型）**：平台模型名完全由渠道模型路由/映射决定，与插件无关——渠道把平台模型映射到某个上游名，该上游名须在插件的有效清单（`meta.models` ∪ `modelsFromConfig` 扩展）内，否则请求 400。**跨插件同名上游模型是正常形态**（同一模型由官方与多家聚合商提供）：请求归哪个插件由渠道绑定的 `plugin_key` 决定，`/pjs` 分发器按它过滤渠道候选，标准端点按渠道调度自然分流；激活/配置保存不做跨插件模型名预检。同名模型共用一套平台定价——用量按宿主固定词汇上报（见「宿主用量词汇」），各家插件都能填出公式用到的键即可（`u()` 缺失取 0）；
- **已移除字段直接拒绝**：`sharedModels`（同名上游模型默认合法，无需声明）、`usageSchema`（用量词汇由宿主固定，见下）——出现即编译失败，错误信息带迁移指引；
- **v1 仅接受零 import 的单文件插件**（esbuild 编译期拒绝任何 import）；
- `requestBody`（decode/validateRequest 返回）与 `body`（buildSubmitRequest 返回）限 **50MiB**（容纳 base64 内嵌参考图）；`taskData` / `state` 限 **1MiB**（随每轮轮询落库与序列化，勿放大对象）；均超限拒绝（不是截断）。

## 3. 钩子卡片

通用规则：**抛 `Error` = 插件级失败**（基座转为 4xx/502 透出，消息经脱敏、按 512 字符截断；任务级失败用 `items[].error`）；返回顶层未知字段被拒绝（查拼写）；所有出入参走 JSON 边界。

### ① decodeRequest（必选）｜请求分类归一
- **入参** `{path, method, params?, body?, headers?, files?}`（body 为客户端请求体原文；headers 为客户端请求头的首值，`Authorization` / `Cookie` 已剔除；files 为 multipart 上传文件的引用，见 §4「FileReference」）
- **返回**（二选一）：
  - `{kind:"submit", model, requestBody?}` — model 是**平台模型名**，原样回显（可能是渠道映射别名，不校验 `meta.models`——那是上游模型清单）；非空即可
  - `{kind:"query", taskIds}` — **仅 dynamic 路由**：这是存量任务查询（如 body 里的 ids 列表），分发器改走批量查询渲染（≤100 个）
- **语义**：从原生路径参数/请求体推出模型与归一化请求体；非法请求在此抛错。**解码阶段不知道上游型号**（渠道尚未选定）——按型号的参数约束（时长/分辨率档位等）放 `validateRequest`

### ①′ validateRequest（可选）｜按上游型号校验/修正
- **入参** `{body, params?, model, upstreamModel, channelBaseUrl?}` — `upstreamModel` 是渠道映射后的上游模型名，宿主已校验它 ∈ 插件有效清单（`meta.models` ∪ 扩展）
- **返回** `{requestBody?}` — 非空时**替换归一请求体**（下游 estimateUsage/buildSubmitRequest/parseSubmitResponse 看到修正值；空对象/不返回 = 原样放行）。修正在解码计划上就地生效，与 parseSubmitResponse 回填 `state` / `immediate` 可同时使用
- **调用时机**：渠道选定后、预扣前（抛错 = 请求不可接受 400，未动钱）；`/pjs` 与标准端点两个入口都会经过
- **语义**：decode 只认平台模型名（可能是映射别名），上游型号在这里才出现——按型号的档位校验（时长/分辨率/素材数量）、协议体形定稿（同一中间体按型号映射为不同上游请求）都在此完成。参考 alibaba/hailuo 的实现

### ② buildSubmitRequest（必选）｜构造上游提交请求
- **入参** `{body, params?, model, upstreamModel?, channelBaseUrl, state?}`
- **返回** `{url, method?, headers?, body?}`
- **语义**：url 为相对路径（拼到渠道 baseUrl）或绝对 URL（host 须在白名单）；不声明 `Authorization` 时基座注入 `Bearer <渠道密钥>`（buildQueryRequest 同理），签名类厂商可用 `ctx.apiKey` 计算后声明该头覆盖默认值

### ③ parseSubmitResponse（必选）｜解析受理
- **入参** `{status, path?, params?, model?, responseBody?, body?}` — `body` 为归一后的提交请求体（decode 返回的 requestBody）：响应不含 action 线索时（如标准端点入站，path 是 `/v1/videos` 而非原生路由）由此推断提交形态
- **返回** `{taskId, taskData?, state?}` — **taskId 必填**
- **调用时机**：基座只在上游返回 HTTP 200 时调用本钩子，非 200 直接按上游错误处理（`status` 恒为 200，无需判断）
- **语义**：`taskData` 是上游快照（落库、轮询回带），**每轮被查询结果整体覆盖**；跨轮要存活的数据放 `state`（基座随任务私有数据持久化，轮询时经 `tasks[].state` 回带，不对客户端可见）；`state` 省略 = 保持原值
- **immediate**（可选，同步即完成）：`{status:"SUCCESS"|"FAILURE", taskData?, usage?, artifacts?, failReason?}` — 同步图片 API 等提交即出结果的厂商：任务**免轮询直达终态**，结算/产物与轮询终态同口径；usage/artifacts 语义与 parseQueryResponse 终态一致

### ④ buildQueryRequest（必选）｜构造上游查询
- **入参** `{tasks:[{taskId, taskData?, state?}], model?}`（per_task 恒单元素）
- **返回** `{url, method?, headers?, body?}`

### ⑤ parseQueryResponse（必选）｜解析进度
- **入参** `{status, responseBody?, tasks, channelBaseUrl?}`（tasks 为 echo；channelBaseUrl 为本任务的渠道地址，供构造需鉴权的产物相对路径）
- **返回** `{items:[{taskId, done, progress?, taskData?, state?, usage?, artifacts?, error?}]}`
- **语义**：`done:false` → 进行中；`done:true` → 终态（有 `error:{code,message}` = 失败，否则成功）；items 的 taskId 必须都在本次查询集合内
- **progress**（非终态可选）：上游进度 `number 0~100` 或 `"42%"` 字符串——基座归一化（`"42%"`）落库，经标准查询端点（`/v1/videos`、`/v1/video/generations`）与 renderTask 的 `task.progress` 透出；未上报保持上一轮值，从未上报的任务在 IN_PROGRESS 期间基座给 `30%` 兜底（恒 `0%` 会被误读为卡死，无需伪造进度），成功终态恒为 `100%`；非法值（越界/非数值）按契约错误拒绝
- **status**：恒为 200——基座不透传轮询的 HTTP 状态码，终态一律按 `responseBody` 内容判定；无法识别的响应返回 `done:false`，由任务超时兜底
- **usage**（终态可选）：官方用量 `{output_seconds: 10, ...}`，键必须 ∈ **宿主固定用量词汇**（见下节）——结算按官方计量多退少补，插件对价格世界一无所知（**上游消费/积分等成本信息不上报**，与平台计费无关）

#### 宿主用量词汇（固定）

`estimateUsage`（预扣估算）与终态 `usage` 只能报这些键，计价口径（per_second 矩阵 / 公式 / 素材方案）完全由宿主模型定价决定；未知键整体拒绝：

| 键 | 类型 | 语义 | 计费消费 |
|---|---|---|---|
| `output_seconds` | number | 生成时长（秒） | per_second 秒数 + 公式 `seconds`/`u()` |
| `resolution` | string | 输出分辨率（`720p`/`1280x720`/`4K` 等，宿主归一为 480P/720P/768P/1080P/2K/4K） | per_second 矩阵查价键 |
| `output_count` | number | 产出数量（图片张数/歌曲段数） | `count` 信号 + `u()` |
| `input_image_count` | number | 输入图片数（含首尾帧） | 素材方案 + `u()` |
| `input_video_seconds` | number | 输入参考视频时长（秒） | 素材方案 + `u()` |
| `input_audio_seconds` | number | 输入参考音频时长（秒） | 素材方案 + `u()` |
| `input_tokens` / `output_tokens` | number | token 计量（按 token 计价的上游） | token 结算通道 + `u()` |
| `generate_audio` | boolean | 是否生成音频 | `u()` 取 1/0（定价维度） |

- 预扣时未知的量（如参考视频实际秒数）按上限估算上报，终态按官方 usage 覆盖（多退少补）
- 精度陷阱：官方 usage 存在占位全零时（如 H3 的空 usage 示例），以关键信号（`output_seconds>0`）判定是否可信，见各内置插件实现
- **artifacts**（终态可选）：产物声明 `[{key:"audio", mimeType?, source:{type, path, auth?}}]`——只指路不碰字节，宿主负责搬运与对外交付（见下方「产物交付」）。`path` 是 taskData 内的取值路径：对象字段点分（`data.video_url`），**数组元素必须用下标**（`results[0].url`；`results.0.url` 点分数字形态宿主会兼容解析，但标准写法是下标）。三种上游形态：
  - **公网直链**：`{type:"url", path:"data.video_url"}`（数组形态如 `path:"results[0].url"`）
  - **需鉴权的二跳 content 端点**（如 sora 的 `/v1/videos/{id}/content`）：把相对路径写进 taskData，声明 `{type:"url", path:"_content_path", auth:"channel-bearer"}`——宿主按渠道 baseUrl 解析并注入渠道密钥（绝对 URL 声明 channel-bearer 时必须与渠道同源）
  - **响应内 base64**：`{type:"inline", path:"data.b64_json"}`，`mimeType` 必填

#### 产物交付（统一内容链接）

成功任务对外一律给**统一内容链接**：`{site_url}/v1/tasks/{publicTaskId}/content[/{key}]?expires=&signature=`——平台签名直链，免 API Key 可直接打开（浏览器 / `<video>` / 下游拉取），有效期由系统设置 `task_content_url_ttl_minutes`（默认 1440 分钟）控制，每次查询任务都会签发新链接。

- **渲染期替换**：renderTask / renderTasks 收到的 `task.data` 中，artifacts 声明路径的值已被替换为对应产物的统一链接（不落库），读原字段即可（如 `data._video_url`）；`task.contentUrl` 另给主产物链接（主产物 = key 为 `video` → 首个 `video/*` → 首个）
- **标准端点**：`GET /v1/videos/{id}` completed 时附扩展字段 `video_url`；`GET /v1/video/generations/{id}` 的 `url` 为统一链接；`GET /v1/videos/{id}/content`（需 API Key，官方 SDK `download_content`）供给同一份字节
- **转存开关**：宿主为每个插件注入内置配置项 `artifact_storage`（管理端「配置」弹窗 · 平台分组，默认开启；插件不可声明同名键，可经 `utils.config.get` 读取）
  - 开启：产物下载/解码后转存平台对象存储，统一链接从 OSS 供给（不受上游直链时效影响）；转存未完成或失败（自动重试 5 次）期间实时回源兜底。inline 产物转存成功后 taskData 中的 base64 被清空释放存储
  - 关闭：只登记声明不转存，统一链接访问时**实时回源代理**（直链 / 渠道鉴权端点 / inline 解码）；上游直链过期后不可下载
- taskData 中 url 型产物保留上游原值（回源依据），不再被改写为 OSS 链接
- **完成态门控**（转存开启时）：上游已完成但产物仍在转存 OSS 途中（pending/running/可重试的 failed），对外一律呈现**进行中**——标准端点 `in_progress`/`IN_PROGRESS` + 进度 99%、无链接；renderTask 收到的 `task.status` 为 `IN_PROGRESS`、`progress` 为 `99%`、产物路径值为空串（不泄出上游直链）。转存完成后才给完成态 + 链接，**客户端拿到完成态时链接必然可用**。兜底：任务完成超过 30 分钟仍未转存成功（重试耗尽或积压）即放行完成态，链接改走实时回源。关闭转存的插件不受门控

### ⑥ renderSubmit / ⑦ renderTask（可选）｜客户端渲染
- **入参** `{task:{publicTaskId, taskId, model, status, progress?, failReason?, data?, contentUrl?}}`（成功任务的 `data` 产物路径已替换为统一内容链接，`contentUrl` 为主产物链接，见「产物交付」）
- **字段语义**：`status` 是平台状态枚举 `SUBMITTED / IN_PROGRESS / SUCCESS / FAILURE`（不是上游状态词，对外呈现厂商/OpenAI 状态词需在钩子内映射）；`progress` 是百分比字符串（如 `"50%"`，来自 parseQueryResponse 的 `items[].progress` 上报，未上报保持上一轮值，可能为空）；失败原因在 `failReason`（没有 `error` 字段）；renderSubmit 只收到 `publicTaskId / model / status / contentUrl`
- **返回** `{status?, body}`（缺省 status=200）；**不导出则走默认透传**

## 4. 宿主能力 `utils`（全局注入）

```js
utils.fetch({url, method?, headers?, body?, responseType?})  // 同步阻塞；≤4次/钩子、15s/次、30s/批、1MiB/响应
                                                               // url 支持相对路径（按渠道 baseUrl 拼接，与 build*Request 同语义）或绝对
                                                               // URL（host 须 ∈ 渠道 baseUrl host ∪ meta.allowedHosts）；不跟随重定向；
                                                               // decode/render 等无渠道上下文的钩子内相对路径被拒
                                                               // 鉴权：与渠道 baseUrl 同源的请求由基座注入 "Bearer <渠道密钥>"（相对路径天然同源）；
                                                               // 跨域（allowedHosts 第三方域）不带任何鉴权；插件自设 Authorization 一律剔除
                                                               // responseType="json" 仅当响应头 Content-Type 含 json 才解析为对象，否则 body 为字符串
utils.log.info/warn/error(message, fields?)                   // 应用日志 + 任务日志（作者排错生命线）
utils.config.get("key")                                       // 读自己的配置（manifest.config 声明；加密字段已解密；未声明键=undefined）
utils.now()                                                   // 毫秒时间戳
utils.uuid()                                                  // UUID v4
utils.crypto.hmacSHA256(message, secret)                      // → hex 小写（new-api 同名同参）
utils.crypto.jwtSignHS256(claims, secret)                     // → HS256 JWT（exp/nbf 由 claims 给定；Kling AK/SK 适用）
utils.crypto.base64 / base64URL / base64URLDecode(s)
```

**FileReference（文件引用）**：submit 路由接受 multipart/form-data——字段名 `body` 为 JSON 请求体原文，其余文本字段并入 body 顶层，文件字段成为引用。decode 的 `ctx.files` 收到 `[{ref, field, filename, mimeType, size}]`（ref 形如 `request_file:image` / `request_file:image#1`）；插件在 buildSubmitRequest 的 body **任意深度**放占位符 `{__fileRef, encoding:"base64"|"dataUrl", mimeType?, maxBytes?}`，宿主发送前用上传字节替换（编码为 base64 或 dataUrl）——**文件字节永不进入 JS**。上限：单文件与内联总量 64MB，占位符 maxBytes 可更严。插件不承接文件时应在 decode 里显式抛错拒绝（`ctx.files` 非空即报错）——否则上传的素材会被静默丢弃（如图生视频退化成文生视频仍按请求计费）。

**dynamic 路由**：type=dynamic 的路由一型两用——decode 返回 `kind:query` 时按 taskIds 批量查询（渲染钩子缺省 `renderTasks`，入参 `{tasks:[...]}`，未导出则返回默认任务数组）；返回 `kind:submit` 时走标准提交。

**immediate（同步即完成）**：parseSubmitResponse 返回 `immediate` 的任务提交即终态，不走轮询。

**钩子别名（new-api 兼容）**：submit 路由可经 `routes[].decode` 指向任意导出的解码函数（缺省 `decodeRequest`），渲染经 `routes[].render` 指名（submit 响应替换标准输出、query 缺省 `renderTask`）——new-api 插件的指名路由无需改函数名即可迁移。

**标准端点入口（`meta.standardVideos`，可选）**：声明后插件模型可经 **`POST /v1/videos`（OpenAI Videos 协议）与 `POST /v1/video/generations`（通用任务端点）** 提交，无需客户端学习插件原生路由；查询侧 `GET /v1/videos/{id}`、`GET /v1/video/generations/{id}` 对两类入口的任务通用。指向的解码钩子：

- **入参** `{surface, path, body, model}` — surface 为 `openai_videos` / `video_generations`；body 为任务框架**通用任务体**（`{model, prompt, seconds?, references?, images?, metadata:{duration, resolution, size, ratio, aspect_ratio, sound, image, last_frame, ...已知厂商键}, extra?}`；两个标准端点均先归一再进钩子——客户端厂商参数统一经 extra 传入，网关把已知键（可灵 mode/cfg_scale 等）提升进 metadata 后才调用钩子，extra 仅剩未知透传键；`/v1/video/generations` 客户端词汇已收敛为 `{model, prompt, duration, resolution, aspect_ratio, sound, references[], extra}`）；model 为已解析到本插件的模型名
- **参考素材 `references[]`**：`[{role, url}]`，role ∈ `first_frame` / `last_frame` / `reference_image` / `reference_video` / `reference_audio` / `file` / `link`（与 Seedance 2.0、MiniMax H3、万相 wan3.0 的 content/media 角色同词汇；file=文档文件参考、link=网页链接参考，仅 wan3.0 类模型支持，须在 referenceRoles 中声明后承接）。`/v1/videos` 入口已完成协议层校验（角色合法、来源唯一、首尾帧与 reference_* 互斥、协议层数量上限），`file_id` 已解析为签名 URL，官方 `input_reference` 已并入为首项 `first_frame`；**顺序即提示词「图片N/视频N/音频N」编号依据，映射时须保持**。存在 `references` 时它是唯一权威来源——`images[]` / `metadata.image` / `metadata.last_frame` 只是给未升级插件的首/尾帧兼容字段，**不含**参考图，请勿与 references 叠加。模型特有约束（数量、音频须搭配图/视频、视频是否收 base64 等）由插件在 decodeVideos 中校验并抛错。`/v1/video/generations` 入口的 file_id 由网关解析为签名 URL 后再进钩子（与 `/v1/videos` 同链路）。可承接的角色须在 `meta.referenceRoles` 声明
- **返回** 与 decodeRequest 的 submit 形态相同：`{kind:"submit", model, requestBody}`（kind 恒为 submit，无查询语义）
- **模型名分工（勿混淆）**：入参 `model` 是客户端请求的**平台模型名**（由渠道模型映射决定，可为任意别名）。**原样回显，禁止做任何白名单/校验**（`meta.models` 是上游模型清单，与平台名无关）。上游名在渠道选定后出现（`validateRequest` / `estimateUsage` / `buildSubmitRequest` 的 `ctx.upstreamModel`），构造上游请求一律用 `ctx.upstreamModel || ctx.model`；按上游型号的分支/校验放 `validateRequest`，decode 阶段只做与型号无关的体形归一
- **语义**：把通用任务体映射为插件原生 requestBody——下游 `estimateUsage` / `buildSubmitRequest` / `parseSubmitResponse` 与 `/pjs` 入口完全复用，计费/轮询/结算/产物链路零差别；渲染钩子不参与（标准端点按各自协议渲染响应）
- 未声明 `standardVideos` 的插件经标准端点提交会得到 400（错误信息指明原生路由入口与声明指引）；其余端点（`/suno/submit`、厂商原生协议端点等）对 JS 插件模型始终拒绝

**扩展上游模型（`meta.modelsFromConfig`，可选）**：把上游新增模型的接纳从「插件发版」变成「管理后台配置」。声明要求：指向的 config 键须在 `manifest.config` 中声明、类型为 `text`/`string`/`json`、不允许加密。语义：

- **有效清单 = `meta.models`（基线，随版本发布）∪ 配置扩展（部署数据）**——上游模型支持性校验（validateRequest 前的宿主检查）与渠道「获取上游模型」候选列表一律按有效清单
- 配置值每行/逗号分隔一个上游模型名（json 型为数组），去重后上限 100 个；跨插件可重名，保存不做独占预检
- 管理员加模型的完整流程：① 模型管理注册平台模型 + 定价（计费刚性）→ ② 渠道管理加模型路由并把平台模型映射到新上游名 → ③ 插件配置填入新上游名，保存即刻生效（generation 重建）

**渠道绑定**：渠道类型「JS 任务插件」，模型路由（`chn_abilities`）绑定模型 → 渠道；`settings.plugin_key` **必填**（须等于插件的 `meta.key`——创建/更新渠道时强制校验，`/pjs` 分发器按它双重核对请求的插件一致性）。

**fetchMode=batch**：轮询循环把同渠道同插件的全部未终态任务**打包成一次** `buildQueryRequest`（`ctx.tasks` 携带整批引用），插件返回的 `items[]` 按上游任务 ID 各自映射终态/用量/产物——**上游未回报的任务请省略对应 item**（返回 done:false 也合法，等价"仍在处理"）。批量上游（如 Suno 的 `/fetch` ids 列表）借此把 N 次轮询收敛为 1 次。

**计费**：模型在管理端配置定价（per_second 矩阵 / formula 公式 / 素材方案），插件按**宿主固定用量词汇**上报「用了多少」（提交时 `estimateUsage` 预扣估算、终态 `items[].usage` 官方事实多退少补）。`estimateUsage` 抛错、返回非对象或上报词汇外/非法的用量键会**拒绝提交**（502，未动钱），不再回落默认价——估算缺失会让公式计价的 `u()` 取 0、预扣落到下限；未导出该钩子时按模型级默认价预扣。公式里的 `seconds` 与 `image_count` 结算时同样取官方值——例：模型公式 `fixed(0.1) * u("output_count")` + 终态 `{output_count:2}` → 本次 0.2 本位币。固定词汇键启动即注册为公式 `u()` 变量；**改定价只改公式/矩阵，插件零改动。**

## 6. v1 边界（明确不支持的）

- **任务取消（Cancel）明确不支持**：任务一经上游受理只能等待终态（成功/失败）或由平台的超时兜底网按失败终态化并退款，v1 不设取消钩子、不透传任何取消语义。
- 流式响应转换、SSE——在后续版本以可选字段增量扩展（破坏性变更升 apiVersion 2）。
- manifest 的 `author` 兼容字符串与 `{name,url?}` 两种形态，`website`（https）为可选展示字段。

## 7. 实例与隔离（安全边界）

写插件前必须知道基座如何执行你的代码：

- **实例池跨租户复用**：同一插件的多份实例在池中存活，**服务所有租户的请求**。模块作用域（顶层 `let/var/const`、闭包状态）在实例生命周期内常驻——**禁止在模块作用域保存任何请求级/租户级数据**（上个请求的内容可能泄漏给下个请求）。请求级状态请走 `state` 透传容器（parseSubmitResponse 返回、parseQueryResponse 回带）。
- **顶层代码有执行超时**：`export const meta` 求值与实例创建都会执行 plugin.js 顶层，超时（与钩子调用同限）即拒绝——顶层只应做纯声明，不要放耗时计算，更不要写依赖 `typeof utils` 判断的死循环。
- **出网白名单**：`utils.fetch` 与 build*Request 返回的绝对 URL 共用同一白名单 = **渠道 baseUrl host ∪ `meta.allowedHosts`**；相对路径由宿主拼渠道 baseUrl。白名单外的绝对 URL 直接拒绝。
- **重定向行为**：主链路（提交/轮询）允许重定向，但目标 host 必须仍在白名单内（跳出即中止）；Go 运行时跨 host 重定向会自动剥掉 `Authorization` 头，同 host/子域保留——鉴权重定向请用相对路径或显式声明 host。
- **单实例串行**：实例内钩子串行执行（无并发），但你在实例间不共享任何状态，也不要假设两次调用落在同一实例。
