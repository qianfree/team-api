# 协议转换语料采集手册

`corpus-extract` 命令的使用说明：如何把线上真实流量转成协议转换层的测试语料。

---

## 1. 这个工具解决什么问题

协议转换层（`relaykit/relayconvert`）有六层测试防线——wire 保真、能力守恒、金样本、
矩阵守卫、E2E 集成、模糊测试。但这些防线的**输入语料全部是手写的**，而手写语料有一个
无法自我察觉的盲区：**写的人想不到的形状**。

真实客户端（Claude Code、Cursor、各家官方 SDK、自研网关）发出的请求，在嵌套深度、
字段组合、多轮结构上远比人工构造的刁钻。历史上多个「静默能力丢失」bug——多模态内容被吞、
链式 ContentPart 丢失、工具循环断链——都出在手写语料覆盖不到的形状上。

本工具把 `chn_debug_logs`（渠道调试日志）里已经记录的真实报文转成语料文件，
让各层防线用真实形状跑一遍。

### 数据从哪来

渠道调试功能对开启的渠道**逐次尝试**记录四段完整报文：

| 段 | 内容 | 本工具用途 |
|----|------|-----------|
| 段1 | 客户端原始请求 | ✅ **请求侧语料**（转换器的输入） |
| 段2 | 网关发给上游的请求 | ❌ 不用（这是转换的**输出**，见 §6.4） |
| 段3 | 上游原始响应（流式为完整 SSE） | ✅ **响应侧语料**（转换器的输入） |
| 段4 | 客户端最终收到的字节 | ❌ 不用（同上） |

关键点：**四段里只有段1和段3是语料**。段2/段4 是「当时那次转换的输出」，
属于另一种用法（生产一致性校验），本工具不处理。

---

## 2. 快速开始

```bash
# 1) 在管理后台给目标渠道打开「调试日志」，跑一批测试流量

# 2) 先空跑，看采到了什么
team-api corpus-extract --dry-run

# 3) 确认统计合理后正式提取
team-api corpus-extract

# 4) 抽查几个语料文件，确认脱敏效果符合预期

# 5) 采集完毕，关掉渠道的调试开关
```

开发环境用 `go run main.go corpus-extract ...` 等价。

## 3. 第一步：采集调试流量

### 开启调试

管理后台 → 渠道详情 → 编辑，勾选 **启用渠道调试日志**（`debug_log_enabled`）。

配套三个过滤器，可缩小采集范围、避免录下无关流量：

| 字段 | 含义 |
|------|------|
| `debug_log_tenant_id` | 只记录指定租户的请求（0 = 不限） |
| `debug_log_user_id` | 只记录指定成员的请求（0 = 不限） |
| `debug_log_api_key_id` | 只记录指定密钥的请求（0 = 不限） |

三者是 **AND** 关系，未设置（0）的维度不参与过滤。**建议用专用测试密钥采集**，
既精准又避免混入其他流量。

### 采集什么流量

#### 首要原则：别手搓请求

这个工具的**全部价值**在于跳出「写测试的人能想到的形状」。如果用 curl 手搓请求去采集，
形状依然来自我们自己的想象力，与手写语料是**同源盲区**——只是把手写从测试文件
挪到了采集脚本里。

优先级：**真实客户端 > 官方 SDK 脚本 > 手搓 curl**，最后一档只用来补冷门方向。

| 客户端 | 入站格式 | 能采到的特征 |
|--------|----------|--------------|
| Claude Code | claude | 重度工具循环、thinking、长多轮、大 system prompt、prompt caching |
| Codex CLI | responses | Responses 原生形态（其 serde 极严，`function_call` 必带 `arguments` 键） |
| Cursor / Cline / Continue | openai 或 claude | 代码上下文、并行工具调用、结构化输出 |
| Gemini CLI / `@google/genai` | gemini | Gemini 原生 parts 形态、thoughtSignature |
| 官方 SDK（openai-python / anthropic / google-genai） | 各自 | 精确控制特征矩阵，适合补缺口 |

项目历史上那几条 wire 契约坑（Gemini parts 禁 null、SSE 禁 `[DONE]`、codex 严格 serde）
**全部是官方 SDK 挑出来的**，手搓请求根本碰不到。

#### 渠道怎么配才能采全方向

路由是**按模型名选渠道**的。所以要让「Claude 格式的请求打到 Gemini 渠道」，
必须在 Gemini 渠道上挂一个模型，再用 Claude 格式去请求那个模型名。

最小渠道集：OpenAI / Claude / Gemini / Ollama / Responses 各一个，
然后四种客户端格式分别打过去：

| 客户端格式 ↓ \ 上游 → | OpenAI | Claude | Gemini | Ollama | Responses |
|---|---|---|---|---|---|
| openai | 直连 | ✓ | ✓ | ✓ | ✓ |
| claude | ✓ | 直连 | ✓ | — | — |
| gemini | ✓ | ✓ | 直连 | — | — |
| responses | ✓ | ✓ | ✓ | — | 直连 |

打勾的 11 格是转换方向，「直连」也要采（透传路径同样有测试价值）。
**跨原生方向（claude→gemini、gemini→claude、responses→claude/gemini）最容易漏**——
日常没人这么配，必须专门造。

#### 请求侧特征清单

请求侧你能精确控制。建议**先各特征单独一条，再来几条组合**——
线上两种都存在，而结构指纹会把它们算作不同形状。

| 特征 | 怎么触发 | 提示词示例 |
|------|----------|------------|
| 基础对话 | 什么都不加 | 「你好」 |
| 工具定义 | 挂一个 `get_weather` 工具 | 「北京今天天气怎么样」 |
| **多轮工具循环** | 上一条的**第二轮**：带着 `tool_result` 再发一次 | — |
| 并行工具调用 | 挂两个工具，问需要同时查的 | 「北京和上海天气分别怎么样」 |
| 强制工具 | `tool_choice` 指定函数名 | 任意 |
| 图片（data URL） | 上传本地图片 | 「这张图里有什么」 |
| 图片（远程 URL） | 传 http 图片链接 | 同上 |
| 思考 | Claude 开 `thinking` / OpenAI 用 o 系列 `reasoning_effort` / Gemini 开 `thinkingConfig` | 「笼子里鸡兔共 35 个头 94 只脚，各几只」 |
| **联网搜索** | 开 web_search 工具，且问题**必须有时效性** | 「今天有什么 AI 领域的新闻」 |
| 结构化输出 | `response_format` 给 json_schema | 「提取这段文字里的人名和公司」 |
| 停止序列 | 设 `stop` | 任意 |
| 长多轮 | 连续对话 5–6 轮 | 任意 |
| 大 system prompt | 塞几千 token 的系统提示 | 任意 |

两个容易做错的点：

- **多轮工具循环必须真跑两轮**。只发第一轮拿到 `tool_call` 是不够的——真正有价值的
  语料是**第二轮请求**，它包含完整的 `assistant.tool_calls` + `tool_result` 历史结构，
  而工具循环断链的 bug 正出在这个结构的转换上。
- **联网搜索要问有时效性的问题**。问「什么是快速排序」模型不会去搜，
  工具挂了也白挂，采不到 `groundingMetadata`。

#### 响应侧特征：只能诱导

响应形状由模型决定，你只能间接诱导：

| 想采到 | 怎么诱导 |
|--------|----------|
| `finish_reason = length` | `max_tokens` 设成 10 |
| `finish_reason = tool_calls` | 上面的工具调用 |
| 缓存命中（cache_read） | 同一个长 system prompt 连发两次（Claude 需显式 `cache_control`） |
| reasoning tokens | 思考类请求 |
| grounding 元数据 | 时效性问题 + 搜索工具 |

内容过滤与安全拦截不建议刻意触发。

#### 最容易漏的五件事

1. **非流式**。绝大多数客户端默认 `stream=true`，而非流式转换器是**完全独立的代码路径**，
   必须专门发 `stream=false` 的请求。这条排第一。
2. **跨原生方向**（见上面的矩阵）。
3. **Ollama 上游**——要本地起一个 ollama。
4. **Responses 入站**——需要 codex 或专门的 Responses 客户端。
5. **同一特征在不同入站格式下都要采**：`openai__tools` 和 `claude__tools`
   是两份语料、驱动的是不同转换器。

#### 建议顺序

先用真实客户端（Claude Code / Cursor / codex）自然跑一段时间，把主干路径和
「想不到的形状」捞进来；再用官方 SDK 脚本按上面的特征表补缺口；
最后跑一次 `--dry-run` 看方向覆盖表，缺哪补哪。

配一个**专用测试密钥**，用 `debug_log_api_key_id` 过滤，避免混入其他流量。

### 覆盖清单

提取完成后命令会打印**转换方向覆盖表**，对照它补采即可。核对四个维度：

- **四种入站格式**：OpenAI chat（`/v1/chat/completions`）、Claude（`/v1/messages`）、
  Gemini（`/v1beta/...`）、Responses（`/v1/responses`）
- **各上游协议**：至少覆盖 OpenAI / Claude / Gemini / Ollama 各一个渠道
- **流式与非流式**：两者的转换器是完全不同的代码路径，都要采
- **能力维度**：工具调用、多轮工具循环、图片、思考、联网搜索

### 注意事项

- **体积**：`chn_debug_logs` 的 body 字段**完整不截断、无自动过期**。带 base64 图片的
  请求单条可达数 MB。这是一次**时间盒式的采集战役**（比如几小时或到 N 条为止），
  不是常开功能。
- **采集完及时关闭调试开关**，并按需清理表数据（无自动清理机制）。
- **脱敏默认开启**：报文体会做内容脱敏（详见 §7）。`--no-scrub` 可关闭，
  但那样落盘的是原文，仅限确知无敏感数据的测试流量。

## 4. 第二步：提取语料

### 命令与参数

```bash
team-api corpus-extract [选项]
```

| 选项 | 默认值 | 说明 |
|------|--------|------|
| `-o, --output` | `relaykit/relayconvert/register/golden` | 语料输出根目录 |
| `--since` | 无 | 起始时间，支持 `2026-09-01` / `2026-09-01 10:00:00` / RFC3339 |
| `--until` | 无 | 结束时间，格式同上 |
| `--channel` | 无 | 渠道 ID 过滤，逗号分隔，如 `3,7,12` |
| `--format` | 无 | 客户端格式过滤：`openai` / `claude` / `gemini` / `responses` |
| `--limit` | `5000` | 最多扫描的日志行数 |
| `--per-shape` | `1` | 每种结构形状保留几条样本 |
| `--max-inline` | `8192` | 内联 base64 超过该字节数则替换为占位（**仅 `--no-scrub` 时生效**；脱敏开启时所有内联数据都会被换掉） |
| `--no-scrub` | 关 | 关闭脱敏，落盘报文原文（仅限确知无敏感数据的测试流量） |
| `--keep-tool-names` | 关 | 脱敏时保留自定义工具名原值（内置工具名始终保留） |
| `--include-errors` | 关 | 包含失败尝试（默认只取上游 200 的最终尝试） |
| `--dry-run` | 关 | 只统计不落盘 |

默认只取 `is_final = true`（产生客户端响应的最终尝试）且上游返回 200 的记录——
中间失败尝试的段1 与最终尝试相同，段3 则是错误体，不是可用的响应语料。

### 先 dry-run

```bash
team-api corpus-extract --dry-run --since 2026-09-11
```

输出示例：

```
扫描 3271 条日志 → 47 种结构形状 → 61 个语料文件
  跳过 12 条（缺 conversion 协议元数据，可能是非 relay 路径）

转换方向覆盖：
  openai→claude                 18
  openai→gemini                 14
  claude→openai                  9
  gemini→openai                  7
  responses→openai              13
（方向覆盖不全时，补充对应渠道的调试采集再跑一次）

[dry-run] 未写入任何文件
```

**怎么读这个统计**：

- `3271 条 → 47 种形状` 说明去重生效了（真实流量冗余极大，这个压缩比是正常的）。
  如果形状数接近日志条数，说明指纹没起作用，需要排查。
- **方向覆盖表是最重要的一行**。上例缺 `claude→gemini`、`responses→claude` 等跨原生方向，
  说明没有配置对应的渠道组合，需要补采。
- `跳过（缺 conversion）` 少量正常（非 relay 路径的请求）；如果占比很高，
  说明采到的多是非转换流量。

### 输出结构

```
relaykit/relayconvert/register/golden/
├── real_inputs/                           # 段1：客户端请求语料
│   ├── openai__image-tools_a1b2c3d4.json
│   ├── claude__basic_e5f6a7b8.json
│   └── ...
├── real_stream_inputs/                    # 段3：上游流式响应（SSE / NDJSON 原文）
│   ├── claude__thinking-toolloop_c9d0e1f2.txt
│   └── ...
├── real_responses/                        # 段3：上游非流式响应
│   └── gemini__websearch_b3c4d5e6.json
└── corpus_manifest.json                   # 清单与统计
```

文件名格式：`<格式>__<特征>_<结构指纹前8位>.<扩展名>`，与手写语料的
`<格式>__<场景>` 约定保持形似，便于人工浏览归类。

> **为什么与手写语料分目录**：真实语料量大且会持续增长，混进 `inputs/` 会让精选集难以
> 阅读；而且金样本套件对手写目录有「文件名必须匹配已知场景」的校验，
> 真实语料的自动命名会触发失败。

### 读懂 manifest

`corpus_manifest.json` 记录每条语料的来源与统计：

```json
{
  "generated_at": "2026-09-11T23:30:00+08:00",
  "source": { "since": "2026-09-11", "limit": 5000 },
  "stats": {
    "scanned": 3271, "skipped_no_conv": 12, "skipped_empty": 3,
    "shapes": 47, "written": 61
  },
  "directions": { "openai→claude": 18, "openai→gemini": 14 },
  "entries": [
    {
      "file": "real_inputs/openai__image-tools_a1b2c3d4.json",
      "kind": "request",
      "format": "openai",
      "features": ["image", "tools"],
      "shape_hash": "a1b2c3d4...",
      "occurrences": 137,
      "client_format": "openai",
      "upstream_format": "claude",
      "relay_mode": "chat_completions",
      "is_stream": false,
      "model_name": "gpt-4o",
      "source_request_id": "...",
      "source_log_id": 88123,
      "captured_at": "2026-09-11T14:22:31+08:00"
    }
  ]
}
```

**`occurrences` 是最有价值的字段**：该结构形状在采集窗口内出现了多少次，
反映真实流量权重。挑选哪些语料提升进精选金样本时，优先看这个数——
高频形状是线上主干路径，最值得锁死。

`source_log_id` / `source_request_id` 可回溯到 `chn_debug_logs` 原始记录。

## 5. 第三步：使用语料（**待实现**）

> **当前状态**：工具链（采集 → 提取 → 脱敏 → 去重 → 落盘）已完成并有单元测试覆盖；
> **测试接线尚未实现**。本节是可直接照做的实施计划，续作从这里开始。
>
> 前置条件：先按 §3 采一批语料、跑一次 `corpus-extract`，**看过真实语料长什么样**
> 再动手——语料的实际形状会影响下面几个断言的写法。

三项工作，按价值排序。建议顺序 (a) → (b) → (c)。

### (a) 不变量测试（主力价值，先做这个）

**目标**：把能力守恒**从「一条手写满配请求」推广到「几百个真实形状」**。
现有 `capExpectations`（`register/capability_invariant_test.go`）只对着一条人工构造的
满配请求验证过，覆盖的是「写的人想得到的组合」。

**落点**：新建 `relaykit/relayconvert/register/realcorpus_test.go`

**实现要点**：

1. 枚举 `golden/real_inputs/*.json`，文件名前缀即客户端格式（`openai__...` → openai）。
   用 `parseWireRequest`（该文件已有，与宿主 `parseInboundRequest` 同款裸 unmarshal）解析。
2. 对每条语料 × 每个 `From` 匹配的已注册请求转换器，断言：
   - 不 panic；转换失败**允许**（真实流量含畸形请求），但不得返回 `(nil, nil)`
   - 成功时结果必须可 `json.Marshal`（宿主紧接着就要序列化发上游）
3. **能力守恒**：复用 `extractProfile` 提取输入与输出画像，逐维比对：
   - 自定义工具名集合：输出必须是输入的超集（目标格式支持工具时）
   - 图片数、工具循环轮次：不得减少
   - 目标格式表达不了的维度按 `capExpectations` 的既有缺口表跳过
4. 流式同理：枚举 `golden/real_stream_inputs/*.txt`，
   复用 `goldensuite_stream_test.go` 的 `runStreamConverter`。

**注意**：真实语料的转换失败率不会是 0（畸形请求、罕见字段组合）。
不要把「转换失败」当断言失败——**要断言的是「不崩溃」和「成功时不丢能力」**。
如果失败率异常高（比如 >5%），那本身是个信号，值得逐条看。

**验收**：`go test -run TestRealCorpus ./relayconvert/register/` 通过，
且能打印出「N 条语料 × M 个方向，K 条转换失败」的统计。

### (b) 模糊测试种子

**目标**：真实形状作为变异起点，大幅提升 fuzz 的有效覆盖。
目前 fuzz 从手写对抗种子出发，起点仍受限于想象力。

**落点**：`relaykit/relayconvert/register/fuzz_test.go`

**实现**：`addSeedsFromDir` 机制现成，加目录即可：

```go
addSeedsFromDir(f, filepath.Join("golden", "real_inputs"), ".json")
```

注意 `addSeedsFromDir` 按 `<格式>__<场景>` 解析文件名取格式前缀，
真实语料的命名（`<格式>__<特征>_<指纹>`）第一段同样是格式，可直接复用。

流式目标同理加 `real_stream_inputs`。

**验收**：`go test -run XXX -fuzz FuzzRequestConversion -fuzztime 60s ./relayconvert/register/`
无失败；`gathering baseline coverage` 的种子数应明显上升。

### (c) 精选金样本

**目标**：把最有代表性的真实形状锁进字节级金样本。

**做法**：按 manifest 的 `occurrences` 降序挑 **10–20 条**，重命名为
`<格式>__<场景>.json` 放进手写语料目录 `golden/inputs/`，
在 `goldenScenarios`（`goldensuite_test.go`）登记新场景名，
然后 `go test -run TestGoldenSuite -update-golden ./relayconvert/register/` 生成 expected。

> ⚠️ **不要给全部真实语料生成字节级金样本**。几百个 expected 文件会让任何一次有意改动
> 产生巨量 diff，而「审查变化面、确认改 A 方向没有波及 B 方向」正是金样本套件的核心价值，
> 那样就废了。这也是真实语料与手写语料**分目录**的原因。

### (d) 可选：生产一致性校验

段2/段4 目前未被使用（见 §6.4）。若要做，用法是**重构前采集、重构后回放**：
段1 → 当前转换器 → 与段2 比对。需要先给 `Record` 补段2/段4 字段，
并在 manifest 里记录渠道配置快照（系统提示注入、参数覆盖、模型映射都会造成合理差异）。

优先级低于 (a)(b)(c)，等前面跑顺再说。

## 6. 工作原理

### 6.1 结构指纹去重

真实流量冗余极大——一万条记录往往只有几十种结构。直接落盘既臃肿又无益，
因此按**结构指纹**去重，每种形状只留代表样本。

指纹算法（`internal/utility/corpus/shape.go`）递归归一化 JSON：

- **对象**：保留排序后的 key，值递归求形状
- **数组**：逐元素求形状后**游程压缩**，连续相同形状折叠为 `{shape, n}`，
  `n` 按 `1 / 2 / 3 / many` 分桶
- **字符串**：判别式值（`type`、`role`、`finish_reason` 等，决定转换分支）保留原值；
  自由文本（`content`、`text`、`model`、`arguments` 等，见 `freeTextKeys`）折叠为 `#str`
- **数字 / 布尔 / null**：折叠为类型占位

**分桶的意义**：「1 条消息」与「2 条消息」是结构差异要区分；
「50 条」与「51 条」是长度噪音要折叠。

**流式另有一套**（`FingerprintStream`）：逐帧取 `data` 负载的形状，
再对帧序列做游程压缩。不折叠的话，「一次回答 3 个 token」和「300 个 token」
会被算作两种形状，去重完全失效。

> **重要**：指纹**只用于去重判等**——把自由文本折叠成 `#str` 不代表语料里就没有内容，
> 它只是让「内容不同、结构相同」的记录被认作同一形状。所以指纹可以折叠得很彻底。
>
> 指纹在**脱敏之后**计算。脱敏保持结构不变，但会重排 key 顺序、归一化数值格式，
> 在原文上算指纹会让同形状的记录因序列化差异被判成不同形状、去重失效。

### 6.2 特征识别

用于文件命名归类，让人浏览目录时一眼看出语料覆盖了什么能力。

采用**跨格式的通用扫描**——遍历 JSON 的全部 key 与判别式字符串值，
对照标记表（`featureMarkers`）匹配，而非按格式写四套解析器。
各协议表达同一能力的字段名不同但都在这张表里（例如 image 同时认
`image_url` / `inlineData` / `input_image`），新增格式无需改代码。

识别的特征：`tools`、`toolloop`、`image`、`thinking`、`websearch`、`audio`、`file`、
`multiturn`（消息数 > 2）。无特征时命名为 `basic`。

特征只影响文件名，识别偏差不影响语料本身。

### 6.3 体积控制

`--max-inline`（默认 8KB）：超过阈值的 base64 串替换为 1×1 透明 PNG 的 base64。

此选项**仅在 `--no-scrub` 时生效**——脱敏开启时所有内联数据都会被换成占位图，
体积问题一并解决。

**这是体积控制，不是脱敏**。图片/音频的**内容**对协议转换毫无影响（转换器只搬运
`mimeType` 与 `data` 字段），但一张截图的 base64 动辄数 MB，原样落盘会让语料仓库失控。

选择真实可解码的 PNG 而非任意字符串，是为了让图片处理路径（尺寸探测、格式校验）
拿到替身后仍能正常工作，语料不会因替身而走进异常分支。

### 6.4 段2/段4 为什么不用

段2（发给上游的请求）和段4（返回客户端的字节）是**当时那次转换的输出**，
不是输入。它们的用途是另一件事——**生产一致性校验**：

段1 → 当前转换器 → 与段2 比对，差异即行为变化。

但**差异不等于 bug**：渠道配置（系统提示注入、参数覆盖、模型映射）和代码版本
都会造成合理差异。正确用法是**重构前采集、重构后回放**，当作重构的回归网，
而且需要同时记录渠道配置快照才能可靠比对。

本工具目前不做这件事。

## 7. 注意事项

### 脱敏（默认开启）

核心判断：**协议转换器只关心结构，不关心内容**。所以自由文本可以激进替换，
不损失任何测试价值。但「激进」必须止步于两类东西，否则语料会变成**假阳性的来源**——
测试失败了，却不是代码的错，是语料自己坏了。

#### 会被替换的

| 类别 | 处理方式 |
|------|----------|
| 自由文本（`content`/`text`/`instructions` 等） | **等长**填充文本替换 |
| 工具参数（`arguments`/`args`/`input` 子树） | 递归替换值，**保持仍是合法 JSON** |
| 自定义工具名与描述 | 一致映射为 `tool_1`/`tool_2`…（`--keep-tool-names` 可保留） |
| 标识符（`id`/`call_id`/`tool_call_id`/`tool_use_id` 等） | 一致映射，**保留前缀**（`toolu_0001`） |
| 内联 base64 数据 | 换成可解码的 1×1 PNG，保留 `data:<mime>;base64,` 前缀 |
| 远程 URL | 换成 `https://scrubbed.example/resource` |
| 思考签名、加密块 | 固定标记 |
| 凭证形态（`sk-`/`AIza`/`ghp_`/JWT 等） | 无条件替换，**不管出现在哪个字段** |

#### 必须保留的（否则语料失效）

**① 引用一致性** —— 这是最容易做错、也是后果最严重的一条：

- OpenAI：`tool_calls[].id` ←→ `messages[].tool_call_id`
- Claude：`tool_use.id` ←→ `tool_result.tool_use_id`
- Responses：`function_call.call_id` ←→ `function_call_output.call_id`
- **Gemini 没有 id，`functionCall` ↔ `functionResponse` 靠函数名关联** ——
  所以工具名也必须一致映射

打断任何一条，工具循环链就断了。而工具循环恰是协议转换最容易出 bug 的地方，
语料坏掉会让测试报「工具循环丢失」，排查半天发现是语料的锅。

实现上是按原值建映射表、整条记录内全局一致替换；**同一记录的请求与响应共用同一张表**，
保证两个语料文件之间的引用也对得上。

**② 判别式与行为相关字段** —— 原样保留：

- `type` / `role` / `finish_reason` / `stop_reason`：决定转换分支
- `model`：决定模型相关分支（Claude 默认 `max_tokens` 按模型名分档、
  Vertex 按名字是否含 `claude` 选端点）
- 协议内置工具名（`web_search`、`code_execution`、`bash` 等）：
  转换器按名识别服务端工具，改掉语料就不再触发那些能力分支
- 数字与布尔（`max_tokens`、`temperature`、`usage`）：影响转换且不含隐私

**③ 形态约束**：

- tool 的 `arguments` 是**JSON 字符串**，替换后必须仍是合法 JSON——
  否则转换器走进解析失败分支，语料反映的就不是线上行为
- 自由文本按**字节长度**等长替换——token 估算（2 字符/token）、截断阈值、
  grounding 的字节偏移校正都与长度相关，长度塌缩会丢掉这些路径的覆盖

#### 已知代价

脱敏经过「解析 → 改写 → 重新序列化」，输出的 key 顺序与空白和原文不同。
语料本就要被转换器重新解析，语义等价即可；但这意味着**脱敏后的语料不适合
做字节级的 wire 保真校验**（重复 key、异常转义之类的原始痕迹会丢失）。
需要那种校验时用 `--no-scrub` 单独采一批。

#### 仍需人工确认

脱敏是启发式的，不是保证。**提交前抽查几个文件**——尤其注意自定义字段：
落在未知 key 下、短且无空格的字符串会按「疑似枚举值」放行。

### 定期刷新

协议在演进（新字段、新能力），旧语料会逐渐偏离现实。建议在大版本升级或
接入新客户端后重新采集一轮。

## 8. 故障排查

**查不到日志**

命令会提示三个检查点：目标渠道是否已开启 `debug_log_enabled`、采集窗口内是否确有流量、
`--since`/`--until`/`--channel` 是否过严。另外注意三个过滤器
（tenant/user/api_key）是 AND 关系，配错会导致一条都录不上。

**形状数接近日志条数（去重失效）**

说明指纹把本应相同的结构判成了不同。常见原因是某个自由文本字段没进
`freeTextKeys`（`internal/utility/corpus/shape.go`）——比如新增的协议字段。
把它加进表即可。

**方向覆盖不全**

覆盖表缺某个方向，说明没有对应的（客户端格式 × 渠道协议）组合流量。
跨原生方向（如 `claude→gemini`、`responses→claude`）尤其容易漏——
需要专门配置一个 Gemini 渠道并用 Claude 格式去请求它。

**某类语料一条都没有**

- `real_responses/` 为空：可能全部流量都是流式的（正常），或上游都没返回 200
- `real_stream_inputs/` 为空：采集的全是非流式请求
- 全部为空但 `scanned` 不为 0：检查 `skipped_no_conv` 是否很高，
  说明采到的是非 relay 路径流量

| 路径 | 职责 |
|------|------|
| `internal/cmd/cmd_corpus_extract.go` | CLI 命令：参数解析、数据库查询、报文解码 |

| `internal/utility/corpus/scrub.go` | 脱敏：一致映射、字段分类、等长替换 |
| `internal/utility/corpus/shrink.go` | 内联数据体积控制（`--no-scrub` 路径） |
| `internal/utility/corpus/corpus_test.go` | 指纹/特征/去重单元测试 |
| `internal/utility/corpus/scrub_test.go` | 脱敏单元测试（重点：引用一致性） |

> 纯逻辑放在 `internal/utility/` 而非 `internal/logic/`，是因为后者会被
> `gf gen service` 扫描并产生噪音文件（`internal/dispatchadapter` 当年正因此被移出
> `internal/logic`）。

**扩展点**：

- 新增协议格式 → 在 `featureMarkers` 补标记词；如有新的自由文本字段，
  同步加进 `freeTextKeys`
- 调整去重粒度 → 改 `bucketCount` 的分桶策略或 `freeTextKeys` 的范围
- 新增语料类别 → 加 `SampleKind` 并实现 `dirOf()` / `ext()`
- **新增协议字段时检查脱敏分类**（`scrub.go`）：承载标识符的加进 `idKeys`
  （否则引用会断）、影响转换分支的加进 `behaviorKeys`（否则语料不再触发该分支）、
  承载用户数据的加进 `userDataKeys`（否则可能漏脱敏）

### 已定决策（不必重新讨论）

这些是实现时权衡过的，改动前先看理由：

| 决策 | 理由 |
|------|------|
| 做成 CLI 而非管理端接口 | 四段报文含请求体原文，不该经 HTTP 出网 |
| 纯逻辑放 `internal/utility/` 而非 `internal/logic/` | 后者会被 `gf gen service` 扫描产生噪音文件 |
| 真实语料与手写语料**分目录** | 真实语料量大且增长；手写目录有「文件名必须匹配已知场景」的校验 |
| 只用段1/段3，不用段2/段4 | 段2/4 是转换的**输出**不是输入；用它们是另一种玩法（§6.4） |
| 指纹在**脱敏之后**计算 | 脱敏会重排 key 顺序，在原文上算会导致去重失效 |
| 脱敏默认**开启** | 安全默认；`--no-scrub` 显式选择原文 |
| 工具名默认**替换**、内置名保留 | 自定义名可能泄漏业务逻辑；内置名是转换器的识别依据 |
| `model` 字段**保留原值** | 决定 Claude 默认 max_tokens 分档与 Vertex 端点选择 |
| 不给全部真实语料生成金样本 | 会让「审查变化面」的能力失效（§5(c)） |

### 踩过的坑

- **引用一致性**是脱敏最容易做错的地方，且后果隐蔽：语料坏掉会让测试报
  「工具循环丢失」，排查半天才发现是语料的锅。四种协议的关联方式各不相同，
  Gemini 甚至没有 id、靠函数名关联（§7）。
- **流式指纹必须折叠帧数**。不折叠的话每条流都是独一无二的形状，去重完全失效。
- **tool `arguments` 是 JSON 字符串**，脱敏后必须仍是合法 JSON，
  否则转换器走进解析失败分支，语料反映的不是线上行为。
- **脱敏后的语料不适合做字节级 wire 保真校验**（重新序列化丢失了 key 顺序等原始痕迹），
  需要时用 `--no-scrub` 单独采一批。
