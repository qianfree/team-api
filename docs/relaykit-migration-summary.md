## 一、项目背景

### 当前问题

team-api 的 `relay/` 模块（26,138 行代码）存在以下痛点：

1. **转换逻辑分散**：24 个供应商的协议转换代码散落在各自的 `channel/` 目录，大量重复代码
2. **难以测试**：转换函数缺乏独立测试，依赖完整的 HTTP 链路
3. **维护成本高**：新增供应商需要 5 天开发时间，协议变更适配需要 2-3 天
4. **无法复用**：转换逻辑与 GoFrame/Gin 框架耦合，无法在其他项目中使用

### 解决方案

参考 new-api 项目的 **relaykit 模块化架构**，将协议转换逻辑提取为独立的 Go 模块：

- **零依赖**：不依赖任何框架，纯粹的协议转换库
- **高可测试**：Golden 测试保证字节级精确性
- **易扩展**：注册表模式，新增供应商只需实现接口
- **可复用**：可以开源或在其他项目中使用

## 二、核心架构

### Relaykit 模块结构

```
relaykit/
├── types/                    # 核心类型定义（RelayFormat、EndpointType）
├── relayconvert/             # 协议转换核心
│   ├── convmeta/             #   Meta 接口（宿主信息契约）
│   ├── internal/             #   转换器实现
│   │   ├── oai_chat/         #     OpenAI Chat Completions 转换器
│   │   ├── claude_messages/  #     Claude Messages API 转换器
│   │   ├── gemini_chat/      #     Gemini generateContent 转换器
│   │   └── oai_responses/    #     OpenAI Responses API 转换器
│   ├── request_registry.go   #   请求转换器注册表
│   ├── response_registry.go  #   响应转换器注册表
│   └── text_converter_registry.go  # 文本转换器注册表（统一接口）
└── dto/                      # 数据传输对象（兼容层）
```

### 关键设计

1. **Meta 接口**：宿主应用（team-api）实现该接口，转换器通过它访问渠道信息、模型名称等
2. **Options 快照**：请求级配置快照，避免并发读取配置时的竞态条件
3. **注册表模式**：转换器通过注册表管理，支持运行时查找和多跳转换
4. **StreamState 接口**：有状态的流式转换（如 Gemini → OpenAI 需要累积 tool_use）
5. **Golden 测试**：每个转换器都有 testdata/ 目录存储预期输出，测试时逐字节对比

## 三、迁移策略

### 核心原则

- **零停机**：双轨并行，功能开关控制，随时可回滚
- **降低风险**：分 7 个阶段渐进式迁移，每个阶段独立验收
- **质量保证**：测试覆盖率 ≥ 85%，Golden 测试通过率 100%

### 7 个阶段

| 阶段 | 工作内容 | 预计时间 | 交付物 |
|------|---------|---------|--------|
| 0 | 准备工作 | 3 天 | 功能开关 + 监控配置 + 测试基线 |
| 1 | relaykit 模块骨架 | 5 天 | 类型定义 + Meta 接口 + 注册表 |
| 2 | DTO 迁移 | 5 天 | 类型别名（向后兼容） |
| 3 | 核心转换器实现 | 10 天 | OpenAI ↔ Claude ↔ Gemini + Golden 测试 |
| 4 | 集成到主项目 | 7 天 | RelayInfo 实现 Meta + Handler 调用 relaykit |
| 5 | 迁移其他供应商 | 24 天 | 24 个供应商全部迁移 |
| 6 | 测试与验证 | 14 天 | 单元测试 + 集成测试 + 压力测试 + 灰度验证 |
| 7 | 清理旧代码 | 7 天 | 删除旧转换函数 + 移除功能开关 + 文档更新 |

**总计**：**75 天**（11 周，约 2.5 个月）

## 五、风险与回滚

### 高风险项

| 风险 | 缓解措施 |
|------|---------|
| 转换逻辑错误导致请求失败 | Golden 测试 + 灰度验证 + 监控告警 + 自动回滚 |
| 性能回退导致服务不可用 | 基准测试 + 压力测试 + 流量控制 + P95 延迟阈值告警 |
| 边界情况未覆盖 | 多样化测试用例 + 生产流量回放 + 灰度分批放量 |

### 快速回滚

每个阶段都可以通过**关闭功能开关**实现 < 5 分钟回滚：

```yaml
# 立即回滚到旧代码路径
relaykit:
  enabled: false
  providers: ""
```

无需代码变更，重启服务即可生效。

## 九、决策建议

### 建议批准执行

**理由**：

1. ✅ **风险可控**：分阶段迁移 + 双轨并行 + 功能开关 + < 5 分钟回滚
2. ✅ **收益显著**：开发效率提升 60%，维护成本降低 80%
3. ✅ **方案完善**：7 个阶段 + 75 天时间线 + 详细回滚方案 + KPI 指标
4. ✅ **长期价值**：零依赖独立模块，可开源复用

### 关键成功因素

1. **严格执行 Golden 测试**：每个转换器必须有 3+ 个测试用例
2. **监控先行**：灰度验证前必须配置好成功率和延迟监控
3. **及时回滚决策**：成功率 < 99.5% 或 P95 延迟增加 > 50ms 立即回滚
4. **充分的测试时间**：阶段 6 预留 14 天进行全面测试，不压缩
